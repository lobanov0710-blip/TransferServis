# PUSH-02B — безопасный приём событий обновления заказа

**Дата:** 03.11.2026. **Статус:** отдельный Draft PR поверх [PUSH-02A PR №27](https://github.com/lobanov0710-blip/TransferServis/pull/27), который зависит от №26 → №25. **Всё ещё без Firebase SDK, FCM отправки и сете­вого включения.**

## Реализовано

`PassengerPushEventGate` — потокобезопасная Java-компонента для будущего `FirebaseMessagingService`. Получает `Map<String,String>` и **проверенный текущий заказ** из `PassengerOrderSessionStore`; проверяет:
- общий compile-time `BuildConfig.PASSENGER_PUSH_NETWORK_ENABLED=false` (в рабочем приложении);
- согласие пассажира и действующее системное разрешение;
- `sessionExpiresAt > now`, наличие собственного `sessionOrderId`;
- строгую минимальную схему `PassengerPushEnvelopePolicy`: только `v=1`, `type=passenger_order_updated`, `eventId` UUID, `orderId` UUID того же заказа, **без статуса, телефона, адресов, цены и произвольных дополнительных полей**.

После проверки eventId сверяется с ограниченным **in-memory LRU-подобным журналом** на 128 UUID на текущую сессию с TTL 10 минут. Повторы игнорируются. Смена заказа/срока сессии очищает журнал. При отключении согласия, разрешения или истечении сессии журнал очищается. Метод синхронизирован, без SharedPreferences, токенов и серверных вызовов.

Возвращает только `IGNORE` или `REQUEST_AUTHENTICATED_STATUS_REFRESH`. **Никогда** не переводит заказ в `taken`/`done`, не меняет цену, не выводит FCM-поле на экран, не публикует уведомление и не вызывает сеть. На следующих этапах принимающая служба обязана повторно получить статус через `OrderRepository.getOrderStatus()` с актуальной защищённой сессией. Само событие не является авторитетным источником состояния.

## Тесты

`PassengerPushEventGateTest` на JUnit: default-disabled в текущей сборке, один и тот же eventId, чужой заказ, дополнительный статус/телефон, отказ/разрешение/истёкшая сессия, смена заказа, десятиминутная TTL, 256 событий в минуту и ограничение до 128 идентификаторов, очистка без побочных эффектов. GitHub CI запускается в зависимости от PR №27; **успешность определять только по финальному HEAD**.

## Ограничения и дальнейшая разработка

- Дедупликация **не персистентна**; после перезапуска процесса то же событие может вызвать ещё одно безопасное чтение статуса. Это не гарантия exactly-once доставки, не дедупликация серверных операций.
- Не защищает от расхода сетевых запросов при множестве **уникальных** валидных событий. До production в будущем receiving-service потребуется debounce/rate limit чтений по заказу и безопасная очередь WorkManager/аналог с учётом Android ограничений, после согласования архитектуры.
- Сессионное сравнение использует **защищённый локальный заказ**, проверка принадлежности и прав остаётся на backend. Политика не должна получать orderId из Android intent или подставлять из push в server API.
- Firebase SDK, `google-services.json`, `FirebaseMessagingService`, разрешение `POST_NOTIFICATIONS` на UI, получение FCM token, отображение уведомления и фактическое обновление экрана **отсутствуют**.
- Для подключения нужно отдельно согласовать Firebase app IDs, безопасный server revoke-only grant, PHP/Worker rollout, дату и политику данных. **PRODUCTION — основное окружение; STAGING — лишь для тестирования по отдельному разрешению.**

PR не меняет `master`, сервер, сайт, production D1, driver FCM, APK и не запускает никаких реальных заказов/уведомлений. Слияние и выпуск — только после подтверждения владельца.
