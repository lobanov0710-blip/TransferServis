# Transfer Servis — детализация ТЗ варианта Б: управление бронированием и пожелания

**Дата:** 03.11.2026  
**Версия документа:** 0.1 (проект уточнений к [ТЗ v0.2](PASSENGER_APP_TECHNICAL_SPEC_V0_2.md))  
**Статус:** **Техническая проработка; продуктовый объём BOOK и PREF утверждён, конкретные бизнес-условия не утверждены.**  
**Репозитории:** TransferServis (Java/XML), public_html (PHP HTTPS/HMAC), uber-v3 (Worker/D1), TransferDriver (назначенный водитель).  
**Неприкосновенные правила:** v1 API FROZEN; D1 — источник истины для orders/quotes, quoteId однократный, цена авторитетна на сервере, `orders.status` остаётся `new / taken / in_progress / done / canceled`; одна локальная защищённая сессия пассажирского заказа.

## 1. Фактическая основа (проверено по исходникам)

- Пассажирский DTO `CreateOrderRequest.java` содержит **только** `quoteId`, `name`, `phone`, `date`, `comment`. Полей времени подачи, числа пассажиров, багажа, кресел, животных или дополнительных услуг **нет**.
- В `uber-v3/migrations/0001_transactional_core.sql` таблица `orders` содержит `trip_date` в формате `YYYY-MM-DD`, `comment` длиной до 2000, `status`, `driver_id`, `updated_at`; отдельного `pickup_time` или параметров услуг нет.
- Текущий `uber-v3/docs/API_CONTRACT_V1.md` оставляет пассажирскому созданию только `date` и `comment`. Цена, тариф, маршрут и время пути берутся из серверного quote; клиент не может переопределить цену.
- Действующий пассажирский capability имеет `passenger_order:read` и подходит для безопасного чтения собственного заказа, **но не является готовым разрешением на изменение/отмену**.
- Текущий `TransferDriver/StaffOrderDto.java` читает заказ, статус, водителя и свободный комментарий; структурированных пожеланий в DTO нет.
- Существующие статусы `done` и `canceled` терминальны. Дополнительные статусы заявок на изменение следует хранить **отдельно** и не добавлять в `orders.status`.

### Следствие

Нельзя просто добавить в форму выбора **время подачи** и галочки услуг, отправив их только как `comment`, и считать функционал реализованным: время не участвует в серверном расписании/напоминаниях, а услугам невозможно назначить серверную валидацию, доступность и цену. Реализация требует аддитивного backend контракта и данных; до этого допускается **только UI-проектирование**, но не ложные подтверждения услуг.

## 2. Область согласования

**СОГЛАСОВАНО владельцем (вариант Б):** пассажир может управлять своим бронированием и указать пожелания к поездке.

**Не утверждено:** разрешённые периоды и цена отмены, запрет изменения после назначения, участники подтверждения, изменение адреса/тарифа, возможность переноса без изменения цены, стоимость и гарантированность дополнительных услуг, минимальный интервал до выезда, SLA рассмотрения. В нижеследующих таблицах `РЕКОМЕНДУЕТСЯ` означает безопасную проектную позицию **до решения владельца**, а не утверждённую политику.

## 3. BOOK — управление бронированием

### 3.1. Предлагаемый набор операций

| Операция | Входит в вариант Б | Политика и допустимость |
|---|---|---|
| Просмотр заявки и доступных действий | Да | Сервер возвращает актуальные доступные действия и причины блокировки. |
| Запрос **изменения даты** | Да, детализируем | Не делать мгновенную замену; проверка правил, наличие водителя и новый подтверждённый расчёт при необходимости. |
| Запрос **изменения времени** | Да, технически требует новых данных | Сначала добавить серверно подтверждённое плановое время, часовую зону и согласовать точность. |
| Запрос отмены | Да | До определения политики — **запрос на рассмотрение**, а не автоматическая отмена заказа. |
| Изменение маршрута/адресов/тарифа | Нет автоматического права | Только отдельное решение и новый server-authoritative quote/offer; в первую итерацию не обещать. |
| Самостоятельное изменение цены/назначения водителя | Нет | Запрещено: эти поля остаются серверными. |

### 3.2. Модель статусов запроса, НЕ заказа

Предлагаемый отдельный жизненный цикл `booking_change_requests`:

```text
submitted → under_review → applied
                         ↘ rejected
submitted / under_review → withdrawn (только если сервер разрешает)
submitted / under_review → expired (по отдельной политике)
```

- `submitted` — сервер принял запрос и присвоил ему ID, **но бронирование не изменилось**.
- `under_review` — диспетчер/сервер рассматривает условия.
- `applied` — изменение **атомарно** зафиксировано в авторитетном заказе, с обработкой возможного переназначения водителя и событий уведомлений.
- `rejected` — заказ остался прежним, причина показана без раскрытия приватных данных.
- `withdrawn/expired` — только если будущая политика разрешает.

**Инвариант:** пока статус запроса не `applied`, исходная дата, цена, водитель и `orders.status` сохраняют прежние авторитетные значения. Если отмена подтверждена сервером, только тогда `orders.status = canceled`. Если решение не применяется из-за гонки/изменившегося статуса, `applied` запрещён; необходим корректный отказ или повторное согласование.

### 3.3. Предлагаемая матрица состояния заказа

| `orders.status` | Показывать доступность управления | Автоматическое применение |
|---|---|---|
| `new` | Показать возможность отправить запрос, если server eligibility разрешает. | По умолчанию **нет**; решение владельца. |
| `taken` | Может потребоваться согласование назначенного водителя/диспетчера; правила определяет backend. | По умолчанию **нет**. |
| `in_progress` | **РЕКОМЕНДУЕТСЯ** не предлагать перенос/отмену как немедленное действие; при необходимости — обращение к оператору вне BOOK. | Нет до отдельного решения. |
| `done` / `canceled` | Только просмотр истории изменений. | Запрещено. |

Android не определяет допустимость по собственным часам или сохранённому локальному статусу; источник `allowedActions` — сервер. Отсутствие `allowedActions` от устаревшего backend = скрытые/отключённые операции, а не разрешение на всё.

### 3.4. UI-диалог изменения/отмены

1. Пассажир открывает «Моя поездка», видит фактическое состояние заказа и доступные сервером действия.
2. Нажимает «Изменить» либо «Запросить отмену». Изменение времени показываем только если контракт/сервер поддерживают время подачи.
3. Вводит новую дату и/или время; клиент проверяет тип/формат, сервер — все правила, часовые пояса и доступность.
4. Перед отправкой видит **факт запроса** и возможные последствия. **Никогда** не показываем выдуманную сумму штрафа, бесплатную отмену или гарантированную дату.
5. После POST отображаем `submitted`, а не `applied/canceled`; реальное решение получаем только с сервера. При сетевом тайм-ауте восстанавливаем запрос по ключу идемпотентности/запрашиваем статус, не отправляем новый дубль.
6. При `applied` перечитываем authoritative order и обновляем UI/Room, а не мутируем локальную копию заранее.
7. При `rejected` показываем причину и прежнюю подтверждённую дату/условия.

### 3.5. Дата и время подачи — отдельная зависимость

**Сейчас** `trip_date` — дата без времени. Для переносов по времени и push-напоминаний необходимы новые серверные поля, например:

- `pickup_local_datetime` — введённые локальные дата и время подачи;
- `pickup_timezone` — **IANA time zone** точки подачи, не часовой пояс телефона пассажира;
- `pickup_at_utc` — нормализованный однозначный момент времени (если он однозначно определён);
- `pickup_time_confirmed_at` — когда время подтверждено оператором/сервером, если нужно;
- `order_revision` или иной механизм optimistic concurrency.

Это **предлагаемые поля**, не существующая миграция. Для неоднозначных/несуществующих local times при переходах DST backend требует явного разрешения, не угадывает UTC. Для старых заказов с одной датой время = **неизвестно**, не `00:00`, не придуманное «10:00». Применение выбранного местного времени и доступности машины должно быть согласовано.

### 3.6. Серверная модель и безопасность — предложение

Предложить таблицу или сущность `booking_change_requests`: `id`, `order_id`, `actor_scope`, `type` (`cancel_request` / `reschedule_request`), `payload`, `status`, `idempotency_key`, `expected_order_revision`, `decision_actor`, `decision_note`, `created_at/updated_at/applied_at`. Это **описание контракта**, не D1 SQL, не выполненная миграция.

При каждой операции:
- пассажирский access в отдельном scoped endpoint, не расширять silently read-only v1 token;
- PHP/HMAC gateway сохраняется; извлечение `orderId` из проверенных прав, а не пользовательского произвольного идентификатора;
- backend проверяет атомарность на текущем `orders.status` / `driver_id` / `updated_at` (или revision);
- idempotency key применяется отдельно от исходного `quoteId` и ограничивается заказом/типом/содержимым запроса;
- полные изменения заказов, если затрагивают цену/маршрут, получают **новый одобренный server offer**, не повторно потребляют исходный `quoteId`;
- после решения backend генерирует событие для пассажирского push и согласованного водительского уведомления; push сам не применяет изменение.

## 4. PREF — пожелания к поездке

### 4.1. Поля интерфейса (предложенная структурированная форма)

| Поле | Тип/интерфейс | Серверная семантика |
|---|---|---|
| Количество пассажиров | Необязательное целое, явно заданное пользователем | Проверка диапазона и вместимости по тарифу/фактическому автомобилю. |
| Багаж | Необязательные количество/размер или выбранная категория | Проверка доступной вместимости; единицы и максимумы — `ОТКРЫТО`. |
| Детские кресла | Необязательное количество и тип кресла | Наличие и стоимость — `ОТКРЫТО`, не считать обеспеченным по галочке. |
| Животные | Необязательный флаг + уточнение (вид/переноска) | Правила перевозки, стоимость, требования к животным — `ОТКРЫТО`. |
| Встреча с табличкой | Необязательный флаг + согласованный текст таблички | Услуга и цена требуют подтверждения. Текст содержит потенциальные персональные сведения. |
| Комментарий | Свободный текст в рамках ограничений | Сохраняется как дополнение, **не** как единственное хранилище структурированных предпочтений. |

**Все поля необязательны** и при отсутствии не должны означать обещание услуги или основание для автоматической цены. Для пустого набора пожеланий прежнее бронирование работает в рамках старого v1. Не задавать фиктивные значения вместимости, доплат и возрастов ребёнка до утверждения политики.

### 4.2. Правила цены и подтверждения

Предлагаемый поток:

```text
маршрут + тариф → ввод пожеланий
→ проверка доступности и серверный расчёт/предложение
→ явное подтверждение итоговой стоимости и условий пассажиром
→ одно идемпотентное создание заказа с сохранением подтверждённых пожеланий
→ просмотр только у уполномоченного диспетчера/назначенного водителя
```

- Если все пожелания пусты и backend не поддерживает новую схему: существующий расчёт/quote/order **не изменяется**.
- Если пожелания заданы, но backend не знает их цену/доступность: нельзя молча игнорировать поля, утверждать стоимость или оформлять «подтверждённое дополнительное обслуживание». Показывать «Требуется подтверждение условий» или временно запретить отправку структурированных предпочтений, пока новая серверная схема не готова.
- Для влияющих на стоимость пожеланий **server quote / отдельный authoritative offer** должен включать соответствующий набор параметров, версию цены и условия; если набор/цена меняются, пассажир подтверждает новое предложение.
- Одно и то же пожелание не должно дублироваться в цене или заказе при retry.
- Подтверждение услуги и сам факт выбора — **разные состояния**: `requested`, `confirmed`, `unavailable` (набор и терминология подлежат contract review).
- Не допускается изменение стоимости в Android после оформления; изменения оформляются через согласованный BOOK-процесс.

### 4.3. Предлагаемая модель данных

В отдельной схеме `order_preferences` / `quote_preferences` (название согласовать): `order_id / quote_id`, нормализованный набор `passengers`, `luggage`, `child_seats`, `pets`, `meet_sign`, `note`, статус подтверждения и привязка к серверному предложению цены, timestamps, audit/version. Секреты и приватная переписка не входят.

**Не использовать массив значений в `orders.comment` как временную псевдосхему**, которая потом будет считаться официальной: невозможно надёжно проверить число кресел, услугу и цену; это риск ложных обещаний пассажиру.

### 4.4. Роли и представление

- Пассажир вводит и видит **собственные** предпочтения и статус подтверждения (если разрешает отдельный API).
- Диспетчер/администратор видит необходимые данные для распределения автомобиля и может подтвердить/отклонить услуги по серверным полномочиям.
- Назначенный водитель получает минимально необходимые данные по своему активному заказу (например, наличие кресел/багажа); после перепривязки доступ прежнего водителя отзывается.
- Пожелания с ФИО на табличке/особенными потребностями считаются чувствительной персональной информацией; минимизировать показ и хранение, не включать в FCM/логи.
- Не делать boolean `false` значением «нет детского кресла», если пассажир вообще не отвечал: `null/not_specified` и явный отказ от услуги требуют разного отображения.

## 5. Push-уведомления: связь с BOOK/PREF

**Вариант Б утверждает пассажирские push**, но время напоминаний пока не согласовано. Для заказов без подтверждённого `pickup_at_utc` нельзя отправлять напоминание «машина через 30 минут», исходя только из `trip_date`.

Минимальные типы:
- изменение статуса реального заказа или назначения;
- `booking_change.submitted / applied / rejected`;
- подтверждение либо недоступность дополнительных условий, если серверная политика это допускает;
- push напоминания только когда подтверждены дата **и** время и задан интервал/таймзона;
- новые сообщения/вызовы в соответствии с CHAT/CALL.

FCM — **только доставка оповещения**: получив push, Android перечитывает собственный защищённый API, сверяет состояние; не хранит access token или персональные подробности в push payload.

## 6. Предлагаемые дополнительные API (НЕ реализованы)

| Назначение | Условный контракт | Гарантия |
|---|---|---|
| Eligibility чтение | `GET passenger/booking-actions` (путь не утверждён) | На основании capability возвращает `allowedActions` и причины отказа, а не меняет заказ. |
| Запрос изменения/отмены | `POST passenger/booking-change-request` | Отдельная авторизация записи, idempotency, `submitted` ≠ `canceled`. |
| Статус изменения | `GET passenger/booking-change-request/{id}` | Только собственные запросы/заказ, текущее решение сервера. |
| Проверка и цена пожеланий | `POST passenger/quote-with-preferences` | Цена и доступность исходят из backend; серверный quote/offer привязан к набору пожеланий. |
| Создание заказа с подтверждёнными условиями | Новый аддитивный контракт | Не ломает `POST /orders` v1; атомарность order + preferences + offer + one-time quote. |
| Водительская проекция пожеланий | Staff endpoint | Только собственный назначенный заказ и минимально необходимая информация. |

**Имена приведены как псевдоконтракты, это не готовые публичные HTTP URL.** Требуется отдельная согласованная спецификация в `uber-v3` и PHP gateway перед созданием Java-DTO/SQL. Без проверки текущей сети, D1-индексов, лимитов и модельного разделения ресурсов не обещать конкретные latency/SLA.

## 7. Проверки и негативные сценарии

| ID | Проверка | Результат |
|---|---|---|
| BPR-01 | Пассажир отправил отмену | Появился `submitted`, исходный статус заказа неизменен. |
| BPR-02 | Backend применил разрешённую отмену | `orders.status=canceled`, новая операция GPS/chat/call закрывается, push сообщает факт. |
| BPR-03 | После применения запроса клиент потерял сеть и повторил с тем же key | Нет второй операции/уведомления, возвращается тот же результат. |
| BPR-04 | Параллельно водитель принял заказ и пассажир запросил изменение | Backend проверяет актуальный assignment/status/revision, не теряет изменения. |
| BPR-05 | Чужой passenger token запросил изменение/историю | 403, отсутствие утечки параметров чужой поездки. |
| BPR-06 | Некорректная дата/время, DST ambiguity, устаревшее время | Сервер отвергает либо требует уточнения, не назначает фиктивную дату UTC. |
| BPR-07 | Старый заказ без времени | Показывается «Время не указано», нет ложного напоминания. |
| BPR-08 | Необязательные пожелания пусты | Старый сценарий quote/order работает. |
| BPR-09 | Запрошено детское кресло/животное при неизвестной доступности | Приложение **не** обещает услугу; требует подтверждённого серверного решения. |
| BPR-10 | Пожелание влияет на цену | Новая серверная цена явным образом подтверждается до создания заказа. |
| BPR-11 | Устаревший водитель пытается прочитать новые пожелания | Доступ запрещён после reassignment. |
| BPR-12 | Push BOOK/PREF потерялся | При открытии приложения актуальные состояния загружаются с сервера. |
| BPR-13 | Дублирование отправки или изменения набора услуг | Нет двойного заказа/двойной доплаты/двойного использования quote. |
| BPR-14 | Неизвестная схема предпочтений в старом backend | Новые поля не игнорируются молча: клиент сообщает о недоступности новой функции. |

Тестировать на изолированной тестовой среде/моках без создания случайных production-заказов, платных звонков и реальных уведомлений. Реальные E2E только по отдельному разрешению.

## 8. Decision register — требует утверждения владельца

| Код | Вопрос | Безопасный проектный вариант ДО решения | Статус |
|---|---|---|---|
| DEC-01 | Отмена до принятия водителем | Только запрос оператору; не мгновенная отмена | **ОТКРЫТО** |
| DEC-02 | Отмена после принятия, до начала поездки | Только запрос оператору/водителю при допустимости | **ОТКРЫТО** |
| DEC-03 | Отмена после начала поездки | Не предоставлять кнопку автоматической отмены; поддержка/админ отдельно | **ОТКРЫТО** |
| DEC-04 | Перенос по времени | Вводить отдельное подтверждаемое время/часовой пояс; обработка вручную на первом этапе | **ОТКРЫТО** |
| DEC-05 | Изменение маршрута/тарифа после бронирования | Отдельное предложение новой цены, не включать в первый release BOOK без отдельного решения | **ОТКРЫТО** |
| DEC-06 | Стоимость отмены и сроки | Не утверждать «бесплатно» и не показывать сумму до правил | **ОТКРЫТО** |
| DEC-07 | Пассажиры и вместимость | Серверные лимиты по тарифу/машине, конкретные значения ещё неизвестны | **ОТКРЫТО** |
| DEC-08 | Багаж, кресла, животные, табличка | Услуги только после подтверждения и проверки доплат/наличия | **ОТКРЫТО** |
| DEC-09 | Кто подтверждает BOOK/PREF | Предложение: уполномоченный диспетчер/админ, водитель — только в своём назначении | **ОТКРЫТО** |
| DEC-10 | Напоминания до поездки | Не включать, пока нет подтверждённого времени, TZ и интервала | **ОТКРЫТО** |

**Нельзя трактовать этот register как отказ от варианта Б:** BOOK/PREF входят в согласованный scope. Для выполнения требуется закрыть существенные условия выше.

## 9. Разработка: последовательность без изменения production

1. Уточнить DEC-01…10 с владельцем; выпустить журнал конкретных подтверждённых правил.
2. На backend уровне спроектировать только аддитивные D1 миграции/схему времён, booking change requests и preferences, а также отдельные пассажирские scope.
3. В `public_html` согласовать узкие безопасные PHP gateway endpoints без публикации токенов Worker и без изменения существующих v1.
4. В `TransferDriver` добавить проекцию подтверждённых пожеланий только для своего заказа.
5. В `TransferServis` добавить форму пожеланий и UI запросов изменения, используя серверные eligibility + offer, а не локальный авторитет.
6. Расширить passenger FCM и E2E проверки после появления авторитетных событий и подтверждённого `pickup_at_utc`.
7. По отдельному PR для каждого репозитория выполнить unit/contract/security tests и dry run; merge, production deploy и реальные заказы — **только с разрешения владельца**.

**Документ не изменяет** Java, PHP, Worker, конфигурацию Cloudflare, D1 или приложения. Функции здесь описаны, но не реализованы.
