## 2. Назначение, пользовательский сценарий и границы

**Цель:** безопасный междугородний трансфер с надёжным бронированием, подтверждениями статусов, доступом к назначенному автомобилю, перепиской и голосовой связью, возможностью обращения об изменении или отмене заказа, предпочтениями и повторным оформлением маршрута.

**Целевой сценарий:** ввод маршрута → выбор `comfort/business/minivan` → расчёт авторитетной цены → добавление необязательных пожеланий → подтверждение → создание одной заявки → уведомления/карточка заказа → назначение водителя → GPS, чат, звонки → завершение → история и повторное бронирование.

**Сервис:** прежде всего Нижний Новгород ↔ Москва, но UI не должен искусственно запрещать иные поддержанные сервером маршруты.

**Существующая модель:** один локальный профиль пассажира и одна защищённая текущая сессия заказа; история Room на устройстве. Повтор поездки открывает новую форму/новый quote, не восстанавливает старую capability. Привязка избранного к аккаунту и нескольких устройств — `ОТЛОЖЕНО`.

**Важная граница BOOK:** согласовано **управление бронированием как функция**, но конкретные дедлайны отмены/переноса, допустимые статусы, необходимость согласования диспетчером, изменение цены и штрафы **не утверждены**. До определения политики никакого прямого изменения заказа на сервере не вводить; UI может формировать запрос изменения, отображая его отдельный статус, только после принятия серверного контракта.

**Тарифы мобильного приложения:** исключительно `comfort` / «Комфорт», `business` / «Бизнес», `minivan` / «Минивэн». «Комфорт+» исключён.

## 3. Архитектура, которую нельзя ломать

| Репозиторий | Ответственность |
|---|---|
| [TransferServis](https://github.com/lobanov0710-blip/TransferServis) | Java + XML, Fragment, MVVM/LiveData, Retrofit/OkHttp, Room, защищённая сессия AndroidKeyStore/AES-GCM, пассажирский интерфейс. `minSdk=24` не повышать без отдельного решения. |
| [TransferDriver](https://github.com/lobanov0710-blip/TransferDriver) | Принятие и выполнение назначенных заказов, GPS-публикация, чат, входящие/исходящие звонки, FCM водителя. |
| [uber-v3](https://github.com/lobanov0710-blip/uber-v3) | Авторитетные заказы и назначения в Cloudflare D1, проверка staff/passenger access, серверная бизнес-логика, уведомления, новые защищённые API. |
| [public_html](https://github.com/lobanov0710-blip/public_html) | Сайт и существующий HTTPS PHP-шлюз пассажира; серверная передача в Worker по HMAC. |

**Существующий маршрут заказа:** Android → `/api/calculate.php` → расчёт/quote → `/api/order.php` → D1; `/api/order-status.php` → серверное подтверждение статуса своего заказа. Пассажирский клиент не вызывает приватный staff Worker API напрямую. Действующий `API_CONTRACT_V1.md` имеет статус FROZEN: новые контракты добавлять отдельно/с версионированием без скрытого изменения v1.

**Статусы заказа (не менять):** `new`, `taken`, `in_progress`, `done`, `canceled`. Состояния «назначен», «прибыл», «в пути до точки подачи» не выводить произвольно из GPS или из `in_progress` — при необходимости проектировать отдельные подтверждаемые события.

|---|---|---|

**Технические границы:** ориентир GPS 5–10 секунд **не является SLA**; лимиты, срок актуальности и частота выбираются после нагрузочных/батарейных тестов. D1 — источник истины назначения; последнее местоположение живёт в отдельном краткоживущем хранилище без истории трека по умолчанию. Для фонового GPS водителя нужна Android Foreground Service и корректное разрешение пользователя. Пассажирскому приложению GPS-разрешение не требуется для просмотра автомобиля.

| ID | Требование | Критерий приёмки |
|---|---|---|
| CHAT-01 | Переписка один-на-один в рамках одного действующего назначения и `orderId`. | Соседний/чужой заказ и прошлый водитель не могут читать/отправлять сообщения. |

| CHAT-04 | При смене водителя и терминальном статусе новые сообщения запрещаются. | Сервер отклоняет попытки неавторизованных/бывших участников. |

Срок хранения переписки, возможность просмотра истории после поездки, лимиты вложений и доставки — `ОТКРЫТО`. **В первой версии вложения и голосовые сообщения не обещать.**

### 5.3. Два обязательных вида звонка — `СОГЛАСОВАНО`

| ID | Требование | Критерий приёмки |
|---|---|---|
| CALL-01 | «Позвонить» предлагает **«По телефону»** и **«Через интернет»**. | Оба варианта доступны при действующем назначении, отсутствующий канал честно помечается как недоступный. |
| CALL-02 | Обычный звонок открывает системную звонилку через `ACTION_DIAL` с разрешённым сервером номером актуального водителя. | Вызов не совершается автоматически; `CALL_PHONE` для этого сценария не требуется; номер не раскрывается неучастникам. |
| CALL-03 | Интернет-звонок — аудио TransferServis ↔ TransferDriver через WebRTC или технически равнозначный проверенный VoIP-стек. | Разговор проходит по сети без обязательной SIM; есть принять/отклонить, завершить, занято/ошибка, тайм-аут. |
| CALL-04 | Отдельный защищённый signaling, STUN/TURN, Android microphone permission, входящие вызовы через системно допустимый UX, FCM-уведомления. | Вызов проверяет права обоих участников при создании/принятии; фон/заблокированный экран тестируются отдельно. |
| CALL-05 | Интернет-звонок не переключается на тарифицируемый телефонный без явного выбора. | При обрыве VoIP есть предложение позвонить по телефону, но автоматического телефонного вызова нет. |
| CALL-06 | Запись звука по умолчанию отсутствует. | Аудиозапись не создаётся и не сохраняется ни клиентом, ни сервером. |

**Открытые вопросы:** VoIP-провайдер либо собственная инфраструктура, TURN/реле и стоимость, ограничения регионов, требования к входящим звонкам, политика телефонных номеров и юридические согласия.

### 5.4. Общие правила назначенной поездки

- `new`: «Ожидаем назначения водителя»; никаких выдуманных данных водителя.
- `taken`: отображать подтверждённое назначение; карта/чат/звонки только когда сервер удостоверил участников.
- `in_progress`: действующее назначение сохраняет доступ, но описания стадии поездки должны соответствовать данным backend.
- `done/canceled`: остановить GPS-подписку и публикацию, новые сообщения и вызовы запретить; историю заказа сохранить.
- **Reassignment:** моментально отозвать доступ прежнего водителя; не отображать его текущую геопозицию, номер и чат как актуальные.
- **Security:** существующий `passenger_order:read` token не считать универсальным разрешением отправлять чат или инициировать звонок; для write-действий определить отдельную scoped capability или документированную проверку прав на новом API.


### 5.5. Push-уведомления пассажиру — `СОГЛАСОВАНО`

**Отдельный passenger push:** наличие FCM у водителя не означает, что пассажирская регистрация устройства уже реализована. Источник событий — подтверждённые изменения D1/бизнес-события, а не догадка клиента. FCM — недостоверный транспорт доставки с возможной задержкой/пропуском/дублированием; после открытия всегда сверять заказ через API.

| ID | Требование | Проверяемый критерий |
|---|---|---|
| PUSH-01 | Android пассажира регистрирует и отзывает FCM-токен своего устройства безопасно и с привязкой к правам соответствующего заказа. | Чужая регистрация/отзыв запрещена; токены не отображаются в API-ответах и логах. |
| PUSH-02 | События: заказ принят, водитель назначен/изменён, поездка начата/завершена/отменена; когда появится достоверное событие — водитель прибыл. | Уведомления соответствуют подтверждённому серверному состоянию; событие «прибыл» не выводится по приблизительному GPS. |
| PUSH-03 | Напоминание о предстоящем трансфере по расписанию только с согласованным временем/часовым поясом и при разрешённых уведомлениях. | Напоминание не создаёт/не меняет заказ и не отправляется для отменённой поездки; период заранее — ОТКРЫТО. |
| PUSH-04 | Нажатие на push открывает собственный проверенный заказ или его статус без передачи capability в URI. | При истёкшем доступе показано безопасное сообщение, чужой заказ не открывается. |
| PUSH-05 | Соблюдать Android POST_NOTIFICATIONS и настройки пользователя. | При отказе в разрешении приложение полностью выполняет расчёт, заказ и просмотр статуса. |
| PUSH-06 | Уведомления идемпотентны на уровне события/устройства и минимизированы по PII. | Повтор события не создаёт массу дублирующих push; текст не раскрывает лишние данные на экране блокировки. |

**Решение по объёму:** push о новом сообщении и вызове из CHAT/CALL включаются в общую пассажирскую инфраструктуру. Никаких рекламных рассылок/программ лояльности в этом ТЗ.

### 5.6. Управление бронированием — `СОГЛАСОВАНО`

| ID | Требование | Проверяемый критерий |
|---|---|---|
| BOOK-01 | На экране своего заказа показать доступные операции «Запросить изменение» и «Отменить/Запросить отмену» по серверной политике. | Недоступная операция скрыта или заблокирована с понятным объяснением; клиент не выбирает допустимость по местному времени самостоятельно. |
| BOOK-02 | Для изменения: запрос новой даты/времени и, если будет отдельно разрешено, адреса/других параметров. | Изменение не происходит до серверного подтверждения; несогласованные параметры не предлагаются. |
| BOOK-03 | До окончательного подтверждения показать последствия: изменение цены/сборы/смена водителя/условия, если применимо. | Когда условия неизвестны, операция не завершается автоматически и явно отправляется на согласование. |
| BOOK-04 | Для отмены предусмотреть явное подтверждение и различать «запрос отправлен», «отмена подтверждена» и «отказано». | UI не помечает заказ `canceled` на основании отправки запроса или сетевого тайм-аута. |
| BOOK-05 | Сохранить прежнюю idempotency создания заказа по `quoteId` и отдельную идемпотентность запросов изменений. | Retry/двойное нажатие не создают дублей, не возвращают заказ в старое состояние. |
| BOOK-06 | Все операции адресованы только заказу, полученному из проверенных прав пассажира. | Нельзя изменять/отменять чужой заказ по подставленному `orderId`; сервер проверяет права и конкурентные изменения. |
| BOOK-07 | Обеспечить журнал статуса запроса и достоверное уведомление пассажира о результате. | После рестарта запроса и приложения виден фактический статус из backend; никаких ложных «изменено». |

**ОТКРЫТО до backend PR:** правила отмен/изменений, финансовые последствия, возможность управлять заказом после `taken/in_progress`, разбор конфликтов с назначением водителя, участники согласования и право на изменение маршрута. Не считать, что владелец утвердил бесплатную отмену, автоматическое переназначение или неизменную цену.

### 5.7. Избранные адреса и повтор поездки — `СОГЛАСОВАНО`

| ID | Требование | Проверяемый критерий |
|---|---|---|
| FAV-01 | Пользователь сохраняет адреса под собственными названиями («Дом», «Работа» и произвольные метки). | Можно создать/изменить/удалить избранное, пустые адреса не сохраняются. |
| FAV-02 | Избранное — локально на устройстве в первой итерации, без нового логина и серверной синхронизации. | Не требуется доступ к чужим заказам/серверная учётная запись; при отсутствии записей корректный пустой экран. |
| FAV-03 | На главной можно заполнить поля `from/to` из сохранённого адреса. | Выбор адреса не создаёт quote/заказ автоматически; пользователь подтверждает расчёт. |
| FAV-04 | «Повторить поездку» из истории переносит только допустимые исходные маршрутные данные в **новый расчёт**. | Всегда свежий quote и актуальная цена, дата, доступные тарифы; старые quoteId, accessToken, статус и цена не переиспользуются. |
| FAV-05 | Персональные адреса не попадут в логи/аналитику/чужие профили и проходят утверждённую политику хранения/backup. | Удаление данных/очистка приложения предсказуемы; резервирование персональных адресов согласовано. |

**Зависимость:** существующая локальная история может содержать неполные поля, поэтому кнопка повтора должна gracefully fallback на ручной ввод. Для server history из нескольких устройств нужна отдельная identity-модель — не входит в вариант Б.

### 5.8. Пожелания к поездке — `СОГЛАСОВАНО`

| ID | Требование | Проверяемый критерий |
|---|---|---|
| PREF-01 | До отправки заказа пользователь может указать количество пассажиров и багаж. | Поля имеют явные правила диапазона и проверяются сервером; фактические ограничения зависят от выбранного тарифа/машины. |
| PREF-02 | Отметить потребность в детском кресле, поездке с животным, встрече с табличкой и указать уточнение текстом. | Заказ не обещает услугу как гарантированную до подтверждения исполнителем; недоступные услуги обозначены. |
| PREF-03 | Выбранные параметры попадают в подтверждение заявки и проверенную серверную модель, видимую диспетчеру/назначенному водителю. | Пожелания не теряются при переходе между экранами/после рестарта; нет утечки в публичный order-status. |
| PREF-04 | Если пожелание влияет на цену/наличие машины, сервер возвращает обновлённую стоимость и требует повторного подтверждения до оформления. | Android не меняет цену самостоятельно и не отправляет старый quote как будто условия прежние. |
| PREF-05 | Необязательные поля не блокируют простое бронирование, если клиент ничего не указал. | Базовая форма и старый backend-контракт остаются совместимыми; неподдержанный сервером набор не отправляется молча. |
| PREF-06 | Ограничения длины текста, формат/списки допустимых значений и обработка некорректного ввода. | Клиент и сервер одинаково валидируют типы и диапазоны, отклоняют инъекции/недопустимые значения. |

**ОТКРЫТО:** вместимость тарифов, список и стоимость допуслуг, обязательность подтверждения водителем, процедура замены автомобиля, является ли «встреча с табличкой» платной и какие пожелания влияют на сам quote. До согласования не считать сервисы бесплатными или гарантированными.

## 8. Модель данных и API: договоры между репозиториями

### 8.1. Нужные новые данные (схема ещё не создана)

| Объект | Ответственный | Нужное состояние |
|---|---|---|
| Карточки автомобиля и водителя | D1 / admin-операции | Подтверждённая машина, контакт и привязка к staff identity; без выдачи лишних персональных данных. |
| Актуальная GPS-точка | Краткоживущее хранилище | Координаты/точность/capturedAt/assignment owner/TTL, без истории маршрута по умолчанию. |
| Сообщения чата | D1 | order, actor/assignment scope, текст, время, idempotency key, retention после отдельного решения. |
| VoIP call session | Server signaling | Участники и state/TTL/метаданные, без аудиозаписей. |
| Passenger FCM registrations | D1 или иное выбранное безопасное хранилище | Привязка к собственной пассажирской capability/заказу и device installation, отозвать при утрате прав, **без выдачи FCM token клиентам**. |
| Booking change requests | D1 | Жизненный цикл запроса, предполагаемые изменения, основания/решение, idempotency, время, связь с исходным заказом. |
| Trip preferences | D1/quotes+orders по утверждённой схеме | Структурированные поля и подтверждённая стоимость/доступность; не полагаться только на свободный комментарий. |
| Favorites | Локальное хранилище Android | Адреса/подписи без серверной синхронизации на первом этапе. |

### 8.2. Контуры API (названия/версионирование пока не утверждены)

| Контур | Клиент | Контракт и проверка |
|---|---|---|
| Assigned driver + GPS read | Passenger → PHP HMAC → Worker | Проверенная capability **своего** заказа, read-only, актуальное назначение/TTL. |
| GPS publish | TransferDriver → Worker | Staff JWT + D1 ownership/status, проверка GPS-полей. |
| Chat read/send | Оба Android клиента | Отдельное право отправки, per-order/per-assignment, защита от дубликатов и rate limit. |
| VoIP signaling | Оба клиента | Короткие scoped credentials, проверка двух участников, время действия/отмена при изменениях. |
| Passenger FCM registration | Passenger → PHP HMAC → Worker | Аутентификация устройства/заказа с ограниченным scope, обновление/отзыв и правила очистки. |
| Notification events | Worker → FCM | Только подтверждённые события, idempotency, никакой доставки чувствительных секретов. |
| Booking management | Passenger → PHP HMAC → Worker | Новый **запрос операции**, серверная политика, optimistic concurrency, явный результат, запрет чужих заказов. |
| Preferences/quote/order | Passenger → PHP HMAC → Worker | Совместимость с существующим quote и ценой; новые параметры — только через проверенный contract PR и валидную цену. |

**Неизменяемые требования:**
- `POST /calculate`, `POST /orders`, `POST /order-status` и PHP gateway v1 имеют замороженные контракты. Нельзя молча добавить изменение цены, новый способ создания заказов или раскрытие driverId в старом ответе.
- `passenger_order:read` сейчас имеет read-only семантику: для CHAT/BOOK/CALL/PUSH registration нужны явно описанные scoped write-действия с проверкой сервера, не переопределять v1 токен на произвольную запись.
- `orders` и `orders.driver_id` остаются авторитетными в D1, водительские статусы меняются по уже установленным правилам, GPS-state не меняет назначение.
- После перехода `new → taken → in_progress → done/canceled` синхронизировать pending booking modifications с диспетчерскими/водительскими операциями, не допускать гонок «принято на клиенте, отказано сервером».
- Подтверждения пассажира и водительские требования должны идти через проверенный сервер, не только через GUI/FCM.


## 9. Безопасность и конфиденциальность

- Все доступы строго по заказу/актуальному назначению, проверка полномочий на **каждый** запрос. Нет API-поиска GPS/номера по произвольному driverId.
- Passenger/staff credentials не помещать в URI, логи, аналитику, WebRTC signaling payload или FCM сообщения; защищённые хранилища и TLS сохраняются.
- Смена водителя/завершение заказа немедленно отзывает права старого назначения на GPS, текст и VoIP; данные исчезают из активного UI.
- Контент push — минимальный (например, «Статус поездки изменился»), без номера телефона, полного маршрута и персональных данных на экране блокировки по умолчанию.
- Регистрация FCM должна поддерживать смену устройства/токена и revoke, не выдавать один заказ произвольным непроверенным устройствам.
- Избранные адреса и пожелания — персональные сведения; задаётся политика хранения и очистки, они не попадают в текст диагностических отчётов.
- Booking request нельзя применять без серверной политики статуса, цены/последствий и авторизации; сервер предотвращает race, idempotency и повторные запросы.
- GPS краткоживущий и добровольно предоставляемый водителем при активном назначении; не скрытая круглосуточная слежка; контроль Android фоновой службы и уведомления водителя.
- VoIP — защищённая голосовая связь, без записи по умолчанию; переход на тарифный сотовый звонок только после сознательного выбора пассажира.
- Лимиты запросов и защита от спама, replay, инъекций и чрезмерной длины полей; отсутствие доступа к чатам других клиентов.
- Документы о конфиденциальности и согласиях, уведомлениях/геолокации, сроке хранения сообщений и возможных юридических ограничениях требуются до релиза.

| E2E-14 | Недопустимая отмена/параллельный водительский переход | Сервер запрещает и возвращает актуальное состояние; старое назначение/цена не затираются. |
| E2E-15 | Избранное + повтор завершённой поездки | Локальное сохранение/удаление работает; повтор открывает новый расчёт и цену, без старой capability. |
| E2E-16 | Запрос поездки с пожеланиями | Backend валидирует пассажиров/багаж/услуги; при влиянии на цену новый quote/подтверждение, данные видимы уполномоченному водителю. |
| E2E-17 | Старый клиент/сервер без новых полей | В v1 не происходит некорректной записи; новые функции изолированы, старый заказ не ломается. |

**Обязательный контроль:** unit tests, backend contract/auth tests, Android instrumented tests на отдельных AVD, negative authorization и ограниченные E2E; для Worker `npm test` и `wrangler deploy --dry-run` до merge. Отчёт различает CI, staging и production. Не делать реальных звонков, уведомлений или заказов без отдельного разрешения на соответствующий тест.

## 13. Открытые решения: объём варианта Б уже утверждён, детали — нет

**Подробная проработка BOOK/PREF от 03.11.2026:** [заявки на изменение бронирования, подтверждаемое время подачи, пожелания, серверные поля и DEC-01…10](TZ_B_BOOKING_AND_PREFERENCES_RULES_V0_1.md). Проверено по актуальным DTO и D1: в текущем заказе есть `trip_date` без времени, а пожелания существуют только как свободный `comment`; функциональные блоки требуют новой совместимой схемы/контракта перед использованием. ## 14. Правила изменения этого ТЗ

- Версия и дата меняются при изменении scope; решения владельца сопровождаются ссылкой/точной формулировкой.
- Новые предложения сначала получают статус `ПРЕДЛОЖЕНО`, а не автоматически `СОГЛАСОВАНО`.
- Изменение FROZEN API v1, Android minSdk, полномочий пассажира, server-side price и order lifecycle требует отдельного review.
- Каждая реализация имеет критерии приёмки, тесты, подтверждение владельца и подтверждённый факт deploy; документация/CI не равны публикации.
