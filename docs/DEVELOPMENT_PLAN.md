## Существующая основа

Один модуль `app`, Java/XML, Fragment → AndroidViewModel/LiveData → Repository →
Retrofit либо Room/SharedPreferences. Уже реализованы профиль пассажира, расчёт
стоимости, создание заказа, защищённое сохранение доступа, экран активного заказа
и локальная история. Изменения ARCH-06 и ARCH-07 уже объединены в основу.

## Этапы

1. Проверить исходную сборку, unit-тесты и Lint выбранной основы.
2. Исключить `passenger_order_session.xml` из cloud backup и device transfer.
3. Исправить переход к созданному заказу: отдельно отражать успех сервера и
   результат сохранения сессии; при локальном сбое сохранять номер заказа,
   объяснять ограничение восстановления и исключать переход к старой поездке.
4. Синхронизировать подтверждённый сервером статус с Room без изменения схемы;
   отклонять устаревшие ответы и не удалять новую сессию при обработке старой.
5. Объединить текущие правила имени/телефона для профиля и бронирования,
   сохранив существующий API и формат телефона.
6. Проверить перезапуск, поворот, временную ошибку сети, истечение и повреждение
   сессии, несовпадающий orderId и конечные статусы; выполнить Android-тесты.
7. Проверить полный сценарий на согласованном сервере и устройстве, затем
   передать владельцу APK, результаты проверок и изменения на просмотр.

## Принятые границы

- Сохраняется текущая модель одного локального профиля и одной сессии заказа.
- Конечный статус отображается и записывается в историю; автоматическое удаление
  завершённых заказов не вводится без согласованного правила.
- Локальная ошибка хранения не превращает уже созданный сервером заказ в ошибку
  бронирования и не вызывает повторный POST создания заявки.
- Токен остаётся в защищённом хранилище. В навигации можно передавать ожидаемый
  orderId, но не сам токен.
- Серверный контракт и БД сервера не изменяются этой веткой без отдельного
  согласования и доступа к исходникам сервера.

Несколько одновременно доступных заказов, учёт нескольких пассажиров в поездке,
аккаунты/авторизация, платежи и уведомления требуют отдельных требований. Они
не считаются готовыми на основании существующего локального профиля.

## Критерии проверки

- Валидные данные профиля сохраняются и подставляются в бронирование.
- Создание заказа выполняется один раз; сбой локального сохранения виден пользователю.
- После создания открывается только ожидаемый заказ.
- Временная ошибка чтения не уничтожает действующую сессию.
- Ответ старого запроса не заменяет состояние нового заказа.
- Подтверждённый статус совпадает на экране активной поездки и в истории.
- Unit/HTTP-тесты, Lint, debug APK и Android-тесты проходят для рабочей ветки.
- Реальный серверный сценарий проверяется отдельно; его результат не подменяется
  успешной сборкой или тестами MockWebServer.
