# FAV-03 — повтор завершённой поездки из локальной истории

**Дата:** 03.11.2026. **Статус:** feature PR с новой Java/XML функциональностью; до объединения и релиза не готово к production.  
**Основание:** [ТЗ v0.2, вариант Б (PR №21)](https://github.com/lobanov0710-blip/TransferServis/pull/21) и [проект избранного](https://github.com/lobanov0710-blip/TransferServis/blob/docs/passenger-spec-v0-1-20261102/docs/TZ_B_FAVORITE_ROUTES_V0_1.md).  
**Зависимости по порядку:** [FAV-01/PR №22](https://github.com/lobanov0710-blip/TransferServis/pull/22) → [FAV-02/PR №23](https://github.com/lobanov0710-blip/TransferServis/pull/23) → FAV-03 (этот этап).

## Объём изменений

- `RouteDraft` (domain): `from` и `to` из локальной завершённой (`done`) поездки, ограниченные по длине; ничего из `orderId/quoteId/accessToken/date/price/tariffName` не переносится.
- `TripHistoryAdapter` отображает «Повторить поездку» только при `done` и двух заполненных адресах.
- `HistoryFragment` через callback передаёт безопасный черновик в activity-scoped `RepeatRouteViewModel` на базе `SavedStateHandle` (одноразовый Bundle из двух строк) и выбирает существующую нижнюю вкладку Home.
- `HomeFragment` однократно получает черновик, инвалидирует любой старый quote, заполняет `Откуда/Куда`, отображает стандартный `comfort` по умолчанию и просит пользователя проверить тариф/выполнить **новый** расчёт. Сохранённая активная пассажирская сессия и защита `hasPending()` не меняются.
- Новые русские строки, unit-тесты `RouteDraft` и отдельный изолированный UI тест истории → Home без нажатия расчёта/создания заказа.

## Защитные условия

- Никакого автоматического HTTP из истории, никакого прежнего значения quote/цены/тарифа; приложение не создаёт новые заказы при нажатии «Повторить».
- Не расширять до `taken/in_progress/canceled/new`: в первой реализации доступно только `done`, чтобы не запутать текущую поездку.
- Без новой Room миграции: FAV-03 только использует существующие `TripHistoryEntity/TripHistoryDao`; API v1 и структура D1 не изменены.
- Нельзя переносить/access token `PassengerOrderSessionStore` из истории.
- Тесты в GitHub Actions выполняются на **одноразовом Android 15 AVD**, не на реальном устройстве владельца. Production API и реальные push/заказы не используются.
- Избранные **пары** маршрутов не добавляются; это дополнительное UX-решение за пределами FAV-03.

## Критерии приёмки

1. Только `done` + две заполненные строки показывают кнопку «Повторить поездку».
2. На Home после нажатия видны именно эти два адреса; старый `QuoteUiState` сброшен в `IDLE`.
3. Новый расчёт запускается лишь штатной кнопкой «Рассчитать» с прежней проверкой pending-order, сервер формирует новый quote.
4. Новая дата и тариф оформляются заново; не переносятся цена, quoteId, orderId, полномочия предыдущего заказа.
5. Unit/CI/Android UI и регрессия существующей истории проходят без ошибок.
6. Для merge необходимы положительные результаты CI и подтверждение владельца; [PR №22](https://github.com/lobanov0710-blip/TransferServis/pull/22) и [PR №23](https://github.com/lobanov0710-blip/TransferServis/pull/23) объединяются **раньше** текущего PR.

**На момент создания этого документа результаты CI не считаются подтверждёнными: требуется проверить GitHub Actions.**
