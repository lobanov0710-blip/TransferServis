# ARCH-COMMS-01 — Отслеживание назначенного автомобиля и связь с водителем

**Дата решения:** 02.11.2026  
**Статус:** согласованное направление развития, архитектура для будущей реализации; функциональность НЕ реализована и НЕ развёрнута.  
**Проекты:** TransferServis (пассажир), TransferDriver (водитель), uber-v3 (backend), public_html (PHP-шлюз).  
**Область:** активный заказ, назначенный водитель, местоположение, чат, два типа голосового звонка.

## 1. Зафиксированные требования владельца

1. В пассажирском приложении нужен экран «Моя поездка» с картой и положением **только назначенного** автомобиля.
2. Для карты выбран **Mapbox Maps SDK** как целевое техническое решение. Применение SDK в разработке/production обусловлено проверкой применимости и стоимости лицензии именно для отслеживания автомобиля; условия использования нельзя считать согласованными.
3. Нужен встроенный двусторонний чат пассажир ↔ назначенный водитель, привязанный к одному заказу.
4. **Оба способа звонка обязательны:** (а) обычный телефонный звонок через системную звонилку, (б) **голосовой звонок через интернет внутри приложений**. Телефонный звонок не подменяет VoIP и наоборот.
5. Функции связи доступны только при действующем назначении на заказ; соблюдаем конфиденциальность и ограничение прав участников.
6. Разработку вести отдельно от текущего production, без изменения действующей системы бронирования и без автоматического merge/deploy.

## 2. Существующая проверенная основа

- TransferServis: Java + XML, Fragment/MVVM/LiveData, Retrofit, ActiveOrderFragment/ActiveOrderViewModel, Keystore-защищённая сессия одного заказа. Android minSdk=24, не повышать ради SDK без отдельного решения.
- TransferDriver: staff login/JWT, карточка заказа, статусы и FCM; переход на телефонный звонок **пассажиру** через ACTION_DIAL уже существует. Передача GPS, встроенный чат и VoIP ещё не реализованы.
- uber-v3: D1 orders.status и orders.driver_id, атомарное назначение водителя и строгие переходы new → taken → in_progress → done; canceled — терминальный статус по существующим правилам. D1 — единственный источник истины заказа и назначения.
- Пассажирский POST /api/order-status.php через HMAC PHP-шлюз и capability token возвращает свой заказ, но намеренно не отдаёт driverId и персональные данные. API_CONTRACT_V1.md имеет статус FROZEN.
- Отдельный draft PR №15 (Yandex MapKit) НЕ слит; по решению от 02.11.2026 выбор Яндекс MapKit в этом draft **заменён перспективным выбором Mapbox**. PR №15 не изменять/не сливать автоматически; дальнейшее закрытие или переработка — отдельное действие.

## 3. Модули и ответственность

| Компонент | Ответственность |
|---|---|
| TransferDriver — LocationPublisher | Запрашивает разрешение, получает координаты системным Android Location API/FusedLocationProvider, отправляет только для своего активного назначенного заказа; корректно работает с foreground service, останавливается после снятия назначения/завершения. |
| uber-v3 — Tracking API | Проверяет действующую staff-сессию, принадлежность заказа и состояние; принимает валидные GPS-данные, публикует только разрешённую актуальную позицию, ограничивает частоту запросов. |
| Tracking transient store | Хранит **последнюю** точку с коротким TTL и временем измерения. Реализацию (например, Durable Objects) и допустимую точность/частоту выбрать после нагрузочной оценки. Не превращать в историю перемещений. |
| D1 | Авторитетные заказы/назначения, профиль автомобиля/разрешённые контакты, текст сообщений и метаданные голосовых вызовов, если потребуются. GPS-история и аудиозаписи по умолчанию отсутствуют. |
| public_html — PHP API gateway | Сохраняет пассажирский путь Android → HTTPS PHP → HMAC → Worker; отдельные защищённые эндпоинты для новых функций. |
| TransferServis — ActiveTrip/Map | Показывает Mapbox-карту, метку только назначенной машины, время и точность последнего сигнала, неустаревший статус; не требует GPS пассажира для простого показа водителя. |
| TransferServis/TransferDriver — Chat | Обмен текстом с доступом строго по orderId и текущему назначению; серверная проверка каждой операции, уведомления FCM. |
| TransferServis/TransferDriver — Calls | Два независимых способа связи: сотовый звонок и приложение↔приложение через WebRTC/эквивалентный VoIP-стек. |

## 4. Состояния и экран «Моя поездка»

- **new:** заказ создан; назначенной машины нет; карта отслеживания и каналы связи с конкретным водителем недоступны.
- **taken:** водитель назначен; показывать безопасные данные водителя/автомобиля, карту (если есть свежий сигнал), кнопки «Чат» и «Позвонить».
- **in_progress:** карта и связь доступны с теми же проверками; UI различает «водитель едет к вам» и «поездка выполняется» только после появления проверяемых дополнительных событий, не выводить это из одного статуса.
- **done / canceled:** GPS-подписка и отправка прекращаются, новые сообщения/вызовы запрещаются; история заказа сохраняется согласно текущим правилам.
- **Смена водителя:** прежнее назначение немедленно отзывается; старые координаты, доступ к чату и возможности вызова предыдущего водителя не переиспользуются.
- Для устаревших GPS-точек явно показывать время последнего обновления и отсутствие актуальной геопозиции. **Ориентир**, а не обещание: период 5–10 секунд при активном отслеживании, адаптация к батарее/сети; TTL, rate limit и критерий stale согласовать отдельно.
- Данные автомобиля (марка, цвет, госномер, имя водителя и контакт) не выдумывать и не показывать, пока серверная модель и верификация таких данных не реализованы.

## 5. Контракты и авторизация (проект, не готовые URL)

### Водитель → Worker

- Auth: действующая авторизованная staff-сессия (driver), идентичность только из JWT + проверки D1, не из присланного driverId.
- Location publish: GPS lat/lon, accuracy, capturedAt, optional heading/speed; сервер проверяет диапазоны, точность, монотонность/свежесть, rate limit, действующее назначение и статус.
- Chat read/send и signaling для звонка — только текущему назначенному водителю и только по соответствующему заказу.

### Пассажир → PHP gateway → Worker

- Auth: существующая защищённая passenger capability, ограниченная строго одним заказом; PHP HMAC для проксирования.
- Отдельные read-only tracking и assigned-driver presentation API; запросы чата/VoIP должны получать отдельные узко ограниченные права, НЕ превращать текущий read-only passenger token в универсальное право записи без проверки назначения и явного нового контракта.
- Получение актуальной GPS-точки, чата и телефонного контакта — только для своего активного заказа, без доступа по произвольному driverId и без списка водителей.
- Новые API спроектировать как **аддитивное расширение или версионированные маршруты** с отдельной спецификацией и тестами. Не ломать замороженный API v1, существующие quote/order/phone endpoints и хранение сессии.

## 6. Чат

- Двусторонние текстовые сообщения, дата/время, отправитель, состояние доставки (при наличии подтверждения).
- D1 хранит сообщения, ограниченные по orderId; сервер проверяет доступ **при каждом чтении и отправке**, учитывая reassignment и терминальный статус.
- FCM — уведомление о новом сообщении, **не** хранилище и не гарант доставки; после открытия чата клиент загружает сообщения с сервера.
- Лимиты длины/частоты, дедупликация по clientMessageId, пагинация, защита от XSS/инъекций, правила хранения/удаления персональных данных — в отдельном контракте.
- Токены и личные телефоны запрещены в логах и push payload.

## 7. Голосовая связь: ДВА способа

### A. Обычный телефонный звонок

- Кнопка «Позвонить» предлагает «По телефону» и «Через интернет».
- В режиме «По телефону» TransferServis открывает **ACTION_DIAL** с сервером разрешённым номером назначенного водителя; пользователь подтверждает звонок в системном приложении. Отдельное разрешение CALL_PHONE для ACTION_DIAL не нужно.
- Номер доступен только пассажиру активного назначенного заказа. В будущем допустимы подменные номера, если согласована стоимость; операторские тарифы действуют независимо от приложения.
- Существующий звонок водитель → пассажир в TransferDriver не ломать.

### B. Интернет-звонок (VoIP)

- **Аудио внутри TransferServis ↔ TransferDriver**, без набора номера и без обязательной SIM-карты, при наличии интернет-соединения.
- Предпочтительная архитектура: **WebRTC** (шифрованный медиаканал), защищённый signaling/сессия вызова через backend, STUN/TURN для NAT traversal и запасного реле. Конкретный signaling transport, провайдер TURN/SDK, стоимость трафика — определить отдельным техрешением; Mapbox к аудиосвязи отношения не имеет.
- Входящий вызов: FCM для пробуждения/уведомления (не медиа), полноценный экран принять/отклонить, проверка назначения при установке и во время вызова, занято/тайм-аут/отмена, корректная обработка приложения в фоне и Android Telecom/foreground service.
- Доступ к микрофону — по разрешению Android. Передача голосового трафика через интернет может расходовать мобильные данные. **Автоматически переключать VoIP на платный телефонный звонок запрещено**: только явное действие пользователя.
- По умолчанию **не записывать аудио**; если потребуется запись, это отдельное решение о согласиях, хранении и правовых требованиях.
- Проверять безопасность токенов сигнализации, replay, отмену после смены назначения, соединение при слабой сети, аудиофокус/Bluetooth, прерывание системным звонком и безопасность управления на ходу.

## 8. Порядок реализации (план, не отчёт о выполнении)

1. Правовая/финансовая проверка Mapbox для автомобильного отслеживания и выбранного SDK, а также вариантов лицензирования VoIP/TURN; не регистрировать ключи в исходниках.
2. Новая спецификация аддитивных API, модель проверенного автомобиля/контакта, права пассажира/водителя, схема данных и тесты безопасности.
3. Отдельные изменения backend uber-v3 и PHP gateway (только в feature-ветках, без production deployment).
4. В TransferServis добавить карточку назначенного автомобиля и звонок по телефону (ACTION_DIAL).
5. В TransferDriver — безопасный GPS location publisher; в TransferServis — Mapbox-карта и polling/обновление маркера.
6. В обоих Android-приложениях — чат и FCM-события.
7. В обоих Android-приложениях — интернет-звонки WebRTC, signaling, TURN и системная интеграция входящих звонков.
8. Unit/contract/security/instrumented/E2E тесты на изолированных устройствах; отдельная приёмка и разрешение владельца на merge и production deployment.

## 9. Нерушимые ограничения и контрольный лист

- Не менять текущие тарифы (Комфорт, Бизнес, Минивэн), расчёт цены, идемпотентность quote→order, статусы заказа и действующие авторизационные границы.
- D1 остаётся authoritative для orders/driver_id и ролей; transient GPS-store не авторитетен для назначений.
- Телефон и точная геолокация — чувствительные данные: минимизация доступа, TLS, отсутствие в URL/аналитике/логах, запрет выдачи другим заказам.
- Без GPS/контактов/связи показывать честные ошибки и fallback; не запускать звонки/заявки в тестах на production.
- Подписанный APK, релиз, отправка push реальным пользователям и production deployment не входят в этот документ.
- Для каждого технического этапа: отдельные PR соответствующего репозитория, автоматические тесты, явная проверка владельцем перед merge/deploy.
