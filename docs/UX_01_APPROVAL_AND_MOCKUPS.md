**Дата:** 27.11.2026, Москва. **Проект:** пассажирский Android TransferServis.
**Основа:** master, `43abdc8f24eb3bd77140a1b684357d9e34df2aaf`.
**Статус:** владелец утвердил первый пакет после анализа. В этом изменении подготовлены макеты и документация; Android-реализация ещё не выполнялась.

## Решение владельца

После предложения первого пакета владелец ответил: «Утвердить».

Утверждён состав:
1. Карточка текущей поездки выше формы на главной.
2. Компактный ввод маршрута и доступ к избранному.
3. Единые компоненты, типографика и понятные тексты расчёта/подтверждения.
4. Последние проверенные сведения при временной ошибке сети.
5. Один механизм чтения статуса без параллельного дублирования одинаковых запросов.
6. Доступность и визуальная приёмка ключевых экранов.

Согласованный порядок: подготовить макеты → получить визуальное согласование → реализовать Android-изменения → выполнить необходимые проверки → передать результат на приёмку. Согласие на первый пакет не означает, что подготовленные в этом PR макеты уже утверждены.

Дополнительные функции из аналитического предложения (сохранённые пары маршрутов, подсказки адресов, календарь, поддержка, рейсы, sharing, отзывы, PDF, остановки и оплата) этим решением автоматически не включаются. Уже утверждённый вариант Б сохраняется; интеграция push/Mapbox/чата/звонков/BOOK/PREF остаётся отдельной работой с существующими зависимостями.

## Неизменяемая основа

- Java/XML, MVVM/LiveData, Navigation Component, Retrofit/OkHttp, Room, защищённая сессия.
- Три тарифа Android: Комфорт, Бизнес, Минивэн.
- Три нижние вкладки: Главная, Поездки, Профиль.
- Одна локальная сессия и локальная история.
- Авторитетная цена и статусы из backend; контракт v1 сохраняется.
- Приоритет pending recovery; повтор из истории только переносит допустимые тексты в новый расчёт.
- Новый расчёт/создание заказа не запускаются при выборе избранного, переходе по вкладке или перерисовке карточки.

## Требования к будущей реализации

### Главная и общие компоненты

Карточка поездки получает состояние из общего источника; собственный polling не добавляется. Предупреждение о неподтверждённой отправке выше карточки и формы. Компактная иконка избранного сохраняет область нажатия не менее 48×48 dp и отдельную понятную подпись TalkBack для «Откуда»/«Куда». Существующий адаптивный показ тарифов на узком экране сохраняется.

### Последние данные при сетевой ошибке

Сохранять только последние проверенные сведения той же действующей сессии. Показывать время последней успешной проверки; не выдавать эти сведения за обновлённые. Для истёкшей capability, несовпадения orderId и смены сессии нужен безопасный отдельный результат. Локальный кэш не определяет разрешение на будущие операции изменения/отмены.

### Одно чтение статуса

В исходном master restore вызывается из нескольких мест жизненного цикла; requestSequence защищает от устаревшего результата, но сам по себе не объединяет уже начатую сеть. Это риск, установленный по исходникам; фактические дубли на устройстве не измерялись.

Требуется один выполняющийся запрос на одну действующую сессию, совместное использование результата экранами и координация запросов открытия, возврата, ручного обновления и будущего push. Смена сессии инвалидирует старую работу. Необходима проверка числа HTTP-запросов с MockWebServer на открытии/повороте/возврате и совпавших событиях; создание заказа сохраняет отдельную идемпотентность и запрет слепого автоматического повтора POST.

### Визуальная приёмка

Проверить 360/411 dp, размер текста 100/130/200%, TalkBack, клавиатуру, системные панели, длинные адреса, loading/error/empty и сохранение восстановления заявки. PDF/HTML-макеты не подтверждают доступность работающего Android UI: она проверяется после реализации на отдельном AVD и физическом устройстве.

## Граница этого изменения

Меняются только документация и источник макетов. Нет Android-кода, новой миграции, изменения API, секретов, включения FCM, изменения server/runtime, подписи, публикации или слияния. Production — основная среда; STAGING используется только при необходимости изолированного тестирования.

Далее требуется визуальная приёмка этих конкретных экранов. После неё — тематическая Android-ветка. Существующие открытые PUSH/security/release PR не сливаются автоматически и не объявляются завершёнными этим документом.
