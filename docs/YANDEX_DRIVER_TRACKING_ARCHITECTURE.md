# TRACKING-01 — Yandex MapKit для назначенного водителя

**Статус:** архитектура на согласование. Карта, GPS и API пока не реализованы. Production и ключи не затронуты.

## Выбор технологии

Для пассажирского Android-приложения выбран **Yandex MapKit Mobile SDK Lite**. Официальная зависимость (версия на 29.10.2026): `com.yandex.android:maps.mobile:4.45.0-lite`. Полный NaviKit не требуется для показа маркера водителя.

**Блокеры до включения карты:**
1. Бесплатная лицензия MapKit **не разрешает отслеживание транспорта**. Согласовать коммерческую лицензию или официально разрешённый тестовый период с Яндексом.
2. MapKit требует **Android 8.0/API 26+**, пассажирский проект сейчас поддерживает `minSdk=24`. Не менять поддержку Android 7 без решения владельца. Варианты: поднять minSdk отдельным PR либо подготовить технически корректный fallback для устаревших версий.
3. Получить ключ MapKit в кабинете Яндекса, не коммитить его в Git. Ключ в APK доступен для извлечения — применять разрешённые Яндексом ограничения.

Документация: https://yandex.ru/maps-api/docs/mapkit/android/generated/getting_started.html
Лицензия: https://yandex.ru/dev/commercial/doc/ru/concepts/mapkit

## Что уже есть в репозиториях

- `uber-v3`: D1 `orders.driver_id`, переходы статусов `new / taken / in_progress / done / canceled`, авторизация персонала и назначение водителя.
- `uber-v3` `POST /order-status`: PHP gateway HMAC + passenger capability token на **один** заказ. `driverId` намеренно исключён из пассажирского ответа.
- `TransferServis`: `ActiveOrderFragment`, `ActiveOrderViewModel`, DTO `PassengerOrderDto`, но **нет** координат назначенного водителя.
- `TransferDriver`: подтверждённые авторизация/статусы заказа и FCM. В проверенном Android Manifest **нет** разрешений геолокации; передачу координат ещё нужно разрабатывать.
- Привязки D1/KV в Worker существуют, но это не означает наличия работающего GPS-API.

## Модель безопасности

Показывать **только назначенного к данному заказу водителя**:
- `new`: карта скрыта, текст «Водитель ещё не назначен».
- `taken` и `in_progress`: видна карта с актуальным маркером; если позиции нет, показывать «Местоположение пока недоступно».
- `done` и `canceled`: немедленно прекращать обновления и очищать текущую точку с экрана.
- При смене назначения не использовать сохранённые старые координаты; при устаревшем сигнале показывать время последней достоверной позиции и не представлять маркер как актуальный.
- Никаких списков других водителей, выдачи GPS по одному `driverId`, логов маршрутов и истории перемещений.
- Обновления только при видимом экране. Пассажирскому приложению не нужны GPS-разрешения для простого отображения позиции водителя.

## Предлагаемые API (контракт, ещё не реализованы)

### TransferDriver → Worker

Защищённая отправка последней точки по активному назначенному заказу с аутентифицированной сессией водителя. Сервер извлекает личность водителя из действующей сессии и проверяет, что именно он назначен в D1. Принимает широту, долготу, точность и время замера, валидирует формат, свежесть, погрешность, частоту обновлений и статус заказа. Хранит только текущую позицию с коротким сроком хранения, без истории GPS. Запуск разрешений и отправки геоданных — по явному согласию водителя; фоновый трекинг потребует отдельной экспертизы Android foreground service и политики распространения приложения.

### TransferServis → PHP gateway → Worker

Новый отдельный read-only endpoint для пассажира с существующим capability token текущего заказа и проверкой HMAC на внутренней границе PHP/Worker. Worker сам извлекает ID заказа из capability, убеждается, что назначенный водитель совпадает с владельцем актуальной GPS-точки, а поездка ещё активна. Возвращает только признак доступности, координаты, время обновления и точность. Не возвращает ID водителя, персональные данные или токены. Запрет HTTP-кэширования, лимит запросов и закрытый отказ после истечения/отзыва доступа. Реальные URL/JSON-поля согласовать отдельным API PR.

## Последовательность внедрения

1. Согласовать лицензию MapKit, выбор `minSdk` и серверный контракт.
2. `uber-v3` + PHP gateway: staging D1-модель и защищённые endpoints, тесты изоляции заказов.
3. `TransferDriver`: координаты по согласованному lifecycle назначенной поездки, запрос разрешений, тесты без реальных пассажиров.
4. `TransferServis`: карта на экране активного заказа, маркер, состояние нет GPS / устарело, обработка жизненного цикла `MapKitFactory` и `MapView`, локальная конфигурация ключа.
5. Staging E2E: два заказа/два водителя, смена назначения, отмена, потеря сети и GPS, истёкший токен, поворот экрана, изолированный эмулятор + физический Android.
6. Production только после отдельной приёмки и подтверждения владельца. Никаких изменений активных PR №13/№14 в рамках этого документа.

**Правило приёмки:** не допускать отображения координат чужого водителя даже на один запрос; не показывать старые координаты после отмены/переназначения.
