## Что проверено

- Подтверждённый заказ сохраняет успешный результат при сбое локального хранилища.
- Потеря/сброс старого UI не теряет подтверждённую сервером запись истории.
- Старый ответ не заменяет уже сохранённую сессию более нового заказа.
- Неудачная новая попытка бронирования не блокирует доступ к ранее подтверждённой.
- Запись истории ставится в очередь до публикации сессии, обновление статуса не
  теряется из-за опережающего UPDATE.
- Экран подтверждения показывает номер и предупреждение после потери состояния
  ViewModel и пересоздания Activity; переход к прежней поездке не предлагается.
- Профиль действительно сохраняется через форму и остаётся после пересоздания
  и повторного открытия Activity; неверный телефон не записывается.
- AndroidKeyStore/AES-GCM восстанавливает сессию между экземплярами хранилища,
  исключает хранение токена открытым текстом и отклоняет повреждённые данные.
- Условная очистка и сохранение учитывают идентичность заказа, токен и срок.
- Room сохраняет историю после открытия БД заново; обновление статуса не
  меняет исходный снимок поездки и не создаёт неполную запись неизвестного заказа.
- Ожидаемый orderId, смена сессии, задержанные callback/UI/DB-задачи и временные
  ошибки сети проверены в production-координаторе активной поездки.

## Границы исторической проверки

Эти ограничения относятся к историческому прогону выше; последующий STAGING-06 E2E проходил отдельно и описан в актуальном статусе.

Полный серверный сценарий создания/обслуживания реальной заявки не выполнялся:
PHP/backend отсутствует в репозитории, согласованный тестовый API не предоставлен.
HTTP-тесты используют MockWebServer; экранный тест подтверждения получает
синтетический успешный результат и не отправляет POST создания заказа.

Пересоздание Activity и восстановление token-free summary проверены. Убийство
процесса ОС во время незавершённого серверного POST не воспроизводилось: надёжное
восстановление такого запроса требует согласованного серверного контракта
идемпотентности/поиска заявки. Проверка на Android API 37 и физическом устройстве
остаётся отдельным этапом перед выпуском.

Поддержка нескольких активных заказов и серверных аккаунтов не вводилась.
Миграция схемы Room не нужна: таблица и её поля не менялись, добавлен UPDATE статуса.
Позднее объединение функциональной ветки в `master` выполнено через PR №9 по согласованию с владельцем.
