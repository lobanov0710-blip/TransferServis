# PUSH-02C — подтверждённое обновление статуса по сигналу push

**Дата:** 03.11.2026. **Статус:** код и изолированные тесты, Draft PR.  
**База:** [PUSH-02B PR №28](https://github.com/lobanov0710-blip/TransferServis/pull/28) → [PUSH-02A PR №27](https://github.com/lobanov0710-blip/TransferServis/pull/27) → №26 → №25. Главная рабочая ветка репозитория — `master`. PRODUCTION является основной системой, STAGING — только для необходимых испытаний.

## Назначение

FCM — **недоверенный сигнал**, а не источник правды о состоянии заказа. Новая Java-компонента `PassengerPushStatusRefreshCoordinator` готовит будущую связку с FCM, но не подключена к `FirebaseMessagingService` или UI.

1. Берёт только существующую защищённую пассажирскую сессию из `PassengerOrderSessionStore` (Android Keystore), с её собственным `orderId`, `accessToken` и временем истечения.
2. Повторно проверяет пользовательский opt-in, системное разрешение на уведомления и исходный `PassengerPushEventGate` из PUSH-02B.
3. При успешной проверке вызывает существующий `OrderRepository.getOrderStatus(accessToken)` через отдельный интерфейс `StatusReader`; **не использует FCM orderId или токен в качестве полномочия**.
4. Пропускает только подтверждённый ответ сервера с тем же `orderId` и неизменившейся действующей сессией. При отказе согласия/разрешения, смене заказа, просроченном token, HTTP/network ошибке или ответе о другом заказе ничего не сообщает потребителю.
5. Локальный rate limit: максимум один одновременный запрос и не чаще **одного запуска каждые 30 секунд на сессию**. Это защита от лавины уникальных `eventId`, а не SLA обновления статуса. Дополнительная 10-минутная дедупликация eventId из PUSH-02B остаётся в силе.
6. `reset()` сбрасывает dedupe/interval/in-flight generation; `close()` блокирует дальнейшие события и отвергает поздние асинхронные ответы.

### Гарантии и ограничения

- `BuildConfig.PASSENGER_PUSH_NETWORK_ENABLED=false` остаётся в Debug и Release. Конструктор по умолчанию использует отключённый `PassengerPushEventGate`; клиент не выполняет сетевые запросы в текущем приложении.
- Package-private конструктор предоставляет фальшивые `Sessions`/`StatusReader`/`LongSupplier`/условия только для JUnit. Это не production override флага.
- **Нет** Firebase Messaging SDK, `google-services.json`, `FirebaseMessagingService`, обработки настоящих push, уведомлений в UI, новых APK, серверных изменений или реального заказа. Новая компонента ниоткуда автоматически не вызывается.
- Результат `VerifiedStatusListener` выдаётся на потоке обратного вызова репозитория; при будущей интеграции UI обязана повторно проверить актуальность сессии и перейти на main thread. Ни UI, ни Room history этой веткой не изменены.
- Внутренняя дедупликация не персистентна; при рестарте приложения возможен повторный безопасный GET/POST status. Одноразовость выдачи grant и авторизация принадлежат backend, а не этому классу.
- Таймер 30 секунд защищает от частых запросов при разных валидных push, но может отсрочить отображение следующего серверного изменения; экран активного заказа уже имеет ручной Refresh/onResume.
- Реальный FCM не следует включать до выбора Firebase Android app configs, безопасного серверного revoke-only scope, утверждения retention политики и прохождения end-to-end тестов.

## Приёмка

JUnit `PassengerPushStatusRefreshCoordinatorTest` проверяет:
- событие само не подтверждает `taken/done`; только подлинный ответ `OrderRepository` может попасть в callback;
- проверка токена своей сессии и её неизменности, отсутствие выдачи чужого заказа;
- отказ при нет consent, нет OS permission или истёк срок сессии;
- отбрасывание callback после opt-out, смены сессии, `close()` и `reset()`;
- ограничение одного in-flight и 30 секунд на разные уникальные события;
- ошибки сети не создают статус и не удаляют заказ.

Испытания проводятся GitHub Actions на текущем HEAD. **Не считать выполненными, пока CI не завершился `success`.**
