# Transfer Servis — FAV: избранные адреса, маршруты и повтор поездки

**Дата:** 03.11.2026. **Версия:** 0.1 — проект технической реализации.  
**Основание:** [утверждённый вариант Б — ТЗ v0.2](PASSENGER_APP_TECHNICAL_SPEC_V0_2.md), FAV-01…FAV-05.  
**Статус:** техническая спецификация, **код не реализован**, условия SDK/API/production не изменены.  
**Репозиторий:** только `TransferServis` (Android Java/XML, Room, MVVM). `uber-v3`, PHP gateway, D1 production, `TransferDriver` не затрагиваются.

## 1. Проверенная существующая основа

- `data/local/TransferDatabase.java` использует `transfer_servis.db`, **Room version=1, exportSchema=false**; единственная entity — `TripHistoryEntity`. Нет таблиц/DAO избранного.
- `TripHistoryEntity` хранит `order_id`, статус, дату, `from_name`, `to_name`, `tariff_name`, расстояние/длительность/цену. **Нет координат, стабильного API tariff_code, quoteId для повтора**.
- `TripHistoryRepository` защищает локальную историю от неверного восстановления; не модифицировать его запись и восстановление для избранного.
- `HomeFragment` содержит `fromInput`, `toInput`, `tariffToggleGroup`, `swapRouteAddresses()`. В `calculateQuote()` в первую очередь проверяется `PendingOrderNoticeViewModel.hasPending()`; затем вызывается `QuoteViewModel.calculate(from,to,tariff)`. Новый UI не должен обходить это условие.
- `QuoteViewModel.reset()` инвалидирует старый расчёт. Тарифный enum принимает **API-коды** `comfort/business/minivan`; история сохраняет только displayName («Комфорт», «Бизнес», «Минивэн»).
- `HistoryFragment`/`TripHistoryAdapter` показывают поездки, но не умеют повторять маршрут; `nav_graph.xml` содержит существующие «Главная», «Поездки», «Профиль», quote/booking/active.
- `backup_rules.xml` и `data_extraction_rules.xml` **исключают домен `database`** из cloud backup/device transfer. Избранное в той же Room-базе наследует этот запрет, если не менять правила.

## 2. Граница утверждённого варианта Б

**Утверждено:** локальные избранные адреса, выбор адреса в форме и «Повторить поездку» из локальной истории с **новым расчётом**.  
**Уточнение, предлагаемое к приёмке:** отдельно сохранять именованные **пары** «Откуда → Куда» с необязательным кодом предпочтительного тарифа. В контексте «Избранные маршруты» это полезно, но первую реализацию допускается ограничить адресами + повтором из истории.

**Не входит:** синхронизация между устройствами, пассажирская авторизация, повторное использование старого quote, автоматическая заявка, статичная цена, новые тарифы, маршрут с промежуточными точками.

## 3. UX и жизненный цикл

### Избранные адреса

1. Кнопка выбора избранного рядом с полями «Откуда» и «Куда». Внутри экрана управления — добавить, изменить подпись/адрес, удалить с подтверждением.
2. Выбор адреса **заполняет только одно поле**, не инициирует API, не создаёт quote/order.
3. Пустая база — сообщение «Избранных адресов пока нет», кнопка добавления.
4. Непустые текстовые адреса/названия валидировать; предусмотреть дубли, длинные строки, Unicode, ошибку локального хранилища.
5. Открывать избранное как вложенный экран/диалог — без новой нижней вкладки.

### Пары маршрутов (предлагаемый дополнительный UX)

1. «Сохранить маршрут» сохраняет два текстовых адреса в исходном порядке; пользователь может указать метку («Дом — Москва»).
2. Необязательный `tariff_code` допускается только из трёх действующих кодов. Он — UX-предпочтение, не подтверждённая цена или доступность.
3. Выбор пары заполняет оба поля. Обратное направление — через имеющуюся кнопку перестановки адресов.
4. Тексты адресов в паре — собственные снимки, не обязательные foreign keys к двум адресам: удаление одного адреса не стирает пару.
5. Сохранённые пары не содержат `orderId`, `quoteId`, токена доступа, старой цены, статуса.

### Повтор из истории

1. Для записи истории добавить «Повторить маршрут» через callback `TripHistoryAdapter` → `HistoryFragment`.
2. Из `TripHistoryItem` переносить **только** `fromDisplayName` и `toDisplayName` при их непустых значениях, в новый UI `RouteDraft`. Вся старая идентичность и цена не переносится.
3. `tariffName` в истории — русская отображаемая строка, **не передавать её напрямую** в `TariffType.fromApiValue()`. В первой версии новый тариф пассажир выбирает явно; никакого слепого восстановления.
4. Старую дату не переносить. Новый маршрут — это черновик, а не бронирование: нужен явный новый расчёт цены и создание нового заказа обычным flow.
5. При неполных текстовых адресах не выводить «готовый маршрут»; предложить ручной ввод.

### Защита существующего бронирования

- `RouteDraft` может заполнять поля даже при pending-order, но **не** обходить `hasPending()` и recovery. Кнопка расчёта следует действующей блокировке.
- Не очищать защищённую passenger session ради выбора избранного/повтора.
- При изменении адресов и тарифа старый `QuoteViewModel.SUCCESS` нельзя считать quote новой пары; использовать контролируемую инвалидацию `reset()` или эквивалентную проверку равенства inputs. Без автоматического POST.
- Кнопка «Рассчитать» проходит единственный действующий `HomeFragment.calculateQuote()`; далее неизменные quote/booking подтверждения.
- Межэкранный черновик передавать lifecycle-aware `SavedStateHandle` либо привязанным ViewModel, **без** токенов и авторитетных данных заказа.

## 4. Архитектура локального хранилища

Предлагаемые новые сущности и слои:

| Файл | Назначение |
|---|---|
| `FavoriteAddressEntity.java`, `FavoriteAddressDao.java` | Room `favorite_addresses`: `id`, `label`, `address_text`, `created_at_millis`, `updated_at_millis`. |
| `FavoriteRouteEntity.java`, `FavoriteRouteDao.java` | Опционально `favorite_routes`: `id`, `label`, `from_text`, `to_text`, `tariff_code` nullable, timestamps. |
| `FavoritesRepository.java` | CRUD и `LiveData`, выполнение записи в фоне, не влияет на OrderRepository. |
| `FavoriteAddress.java`, `FavoriteRoute.java`, `RouteDraft.java` | Доменные объекты; RouteDraft не содержит id/quote/цену/credentials. |
| `FavoritesViewModel.java` и `FavoritesFragment.java` | Список, создание/редактирование/удаление, UX-состояния и ошибки. |
| `HomeFragment.java` / `HistoryFragment.java` / `TripHistoryAdapter.java` | Подстановка адресов и безопасное действие «Повторить». |

**Схема:** названия/адреса НЕ пустые, timestamp Unix milliseconds, локальные UUID/ID, нормализация пробелов для сравнения. Правила совпадений (метка либо пара/текст) согласовать перед кодом; не выдумывать жёсткие лимиты записей.

### Обязательная Room-миграция 1 → 2

1. В `@Database` добавить только нужные новые entities и увеличить version `1 → 2`.
2. Реализовать явную **`Migration(1,2)`**: создать новые таблицы/индексы **без пересоздания `trip_history`**. Зарегистрировать через `.addMigrations(...)`.
3. **Запрещён** `fallbackToDestructiveMigration()`: он может удалить существующую историю пассажира.
4. Для воспроизводимых миграционных тестов запланировать `exportSchema=true`, схему Room и `MigrationTestHelper` (с настройкой Gradle/test-schemas). Проверить заполненную и пустую базу v1.
5. Не менять existing `TripHistoryEntity` и его DAO/логическую запись в этом feature-PR. Не трогать `PassengerOrderSessionStore`.
6. Не выполнять Room-запросы синхронно на UI thread; ошибка избранного не должна приводить к повторному созданию заказа.
7. Сохранять существующее исключение database из backup/device transfer: локальные адреса не должны копироваться в облако без нового решения владельца.

| ID | Сценарий | Ожидаемое поведение |
|---|---|---|
| FAV-T01 | Обновление заполненной базы v1 → v2 | История, цены, статусы и order_id остались; новые таблицы корректны. |
| FAV-T02 | Пустая v1 → v2 и чистая установка v2 | Нет падений, корректное пустое состояние. |
| FAV-T03 | Добавление, изменение, удаление адреса | Запись сохраняется после поворота и перезапуска. |
| FAV-T04 | Сохранение/выбор пары (если включены) | Откуда и куда не меняются местами; старую цену не храним. |
| FAV-T05 | Выбор любимого адреса в одном поле | Второе поле не меняется; ноль HTTP-запросов. |
| FAV-T06 | Выбор пары при старом quote UI SUCCESS | Старый результат не привязывается к новой паре; новое quote только после расчёта. |
| FAV-T07 | «Повторить» из истории | Только текст адресов; нет старых `orderId/quoteId/status/price/date`, новый расчёт. |
| FAV-T08 | История с русским тарифом и неполными адресами | Никакой ложной конвертации в API-code, ручное уточнение. |
| FAV-T09 | Pending recovery/незавершённая заявка | Блокировка `hasPending()` остаётся, quote/order не создаются. |
| FAV-T10 | Активная passenger session | Избранное не заменяет и не удаляет действующий order token. |
| FAV-T11 | Ошибка Room / отказ сети | Ошибка локального избранного не крашит заказ; список работает офлайн. |
| FAV-T12 | Unicode, пробелы, дубли, длинный адрес | Валидация единая и без утечки PII в Logcat. |
| FAV-T13 | Backup/transfer | База и избранные адреса по-прежнему исключены из резервного копирования. |
| FAV-T14 | Назад/поворот/повторный вход | Никакого скрытого calculate/order POST, нет stale quote и ложного success. |

**Готовность реализации:** unit/DAO/migration instrumented тесты на изолированном Android AVD, lint и Debug/unsigned Release build. Документационный PR не свидетельствует об успешных тестах нового кода. Запуск production-API и создание настоящих заказов в этих тестах не допускаются.
