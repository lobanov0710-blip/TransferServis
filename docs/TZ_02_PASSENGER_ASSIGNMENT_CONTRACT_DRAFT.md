## Предлагаемый контракт

Рекомендуется версионированное чтение `POST /api/v2/order-status.php` → `POST /v2/order-status`. Один ответ содержит статус и данные назначения из того же снимка D1. Действующий [контракт v1](https://github.com/lobanov0710-blip/uber-v3/blob/7fad96a63ac963e6c28bf03f21d52b90e5cb69ff/docs/API_CONTRACT_V1.md#92-post-apiorder-statusphp) продолжает обслуживать существующих клиентов.

| Вариант | Последствие для клиента |
| --- | --- |
| **Рекомендуется: v2 статуса с карточкой** | Одно чтение на обновление. Состояние заказа и карточка согласованы. Нужно выпустить новый маршрут Worker и PHP до включения клиента. |
| Отдельный маршрут только для карточки | Можно вводить независимо. Появляется второй HTTP-запрос и необходимость согласовать два ответа, если назначение изменилось между ними. |

- Запрос принимает только `accessToken` в теле. Worker проверяет HMAC для нового пути и capability пассажира, затем выбирает заказ по `sub` токена. Клиентские `orderId`, `driverId` и `vehicleId` для выбора записи не используются.
- Источник карточки — текущее действующее назначение в D1 и зарегистрированная в нём пара водитель/автомобиль. В одном чтении проверяются состояние заказа, активность назначения и доступность пары по принятым правилам G2, включая действующую блокировку при утрате доверия к автомобилю. Для устаревшего заказа, где есть только `orders.driver_id`, сервер вернёт статус с `assignment: null`.
- Проекция содержит поля заказа, разрешённые в v1, и ревизию заказа. `assignment` содержит разрешённое отображаемое имя водителя и марку, модель, цвет и госномер назначенной машины. При отсутствии разрешённого поля допускается `null`. Использовать только утверждённые для показа сведения из серверного профиля. Правило формирования имени согласуется отдельно от административного `full_name`.
- Прямой контакт в первом срезе не включается. Позднее источник разрешённого номера и правила показа нужны для TZ-03 `ACTION_DIAL`; регистрационный `normalized_phone` не считается разрешением на раскрытие. Тарифный класс выбранной машины не подменяет тариф и цену оформленного заказа.
- Документы, VIN, дата рождения, контакты из регистрации, staff/vehicle IDs и служебные поля не включаются в проекцию. Ответы имеют `Cache-Control: no-store`. Токены и поля карточки исключаются из логов и push.
- Сохраняется семантика чтения статуса v1: `400` для неверного запроса, `403` для недействительной или истёкшей capability, `404` для отсутствующего заказа, `405` для неверного метода, `5xx` для сбоя. Подтверждённое отсутствие назначения возвращает `200` и `assignment: null`, сбой чтения возвращает ошибку.

Пример добавляемых полей внутри `order`. Значения демонстрационные.

```json
{
  "id": "demo-order",
  "status": "taken",
  "revision": 2,
  "assignment": {
    "driverDisplayName": "Демонстрационное имя",
    "vehicle": {"make": "Марка", "model": "Модель", "color": "Серый", "plate": null}
  }
}
```

## Поведение Android

| Состояние | Поведение |
| --- | --- |
| `new`, `done`, `canceled` или назначения нет | Карточка водителя скрыта, статус заказа отображается. |
| `taken` или `in_progress`, назначение подтверждено | Отображаются только разрешённые непустые поля. Частичный ответ не заполняется шаблонными значениями. |
| Перепроверка, временная ошибка, смена сессии или утрата доступа | Карточка не используется из предыдущего ответа. При временном сбое продолжают действовать правила UX-01 для последнего статуса заказа. |
| Переназначение | После свежего ответа заменяется карточка целиком. Ответ старого запроса или другой сессии отбрасывается. |

Клиент выбирает v1 или v2 по конфигурации окружения. Существующий координатор объединяет совпадающие обновления одной сессии. Автоматический запрос v1 после ошибки v2 не нужен: сбой отображается штатно. Android не сохраняет карточку в историю или постоянное хранилище.

## Реализация и приёмка

1. Согласовать маршрут, набор полей и право показа имени. Согласовать безопасный источник контакта отдельно перед TZ-03.
2. После готовности серверной схемы открыть отдельный PR `uber-v3` на актуальной согласованной базе G2. Пассажирское чтение использует существующую модель назначения. Миграция для карточки сама по себе пока не обоснована. Существующий режим OWNER-only STAGING не расширяется в рамках этого контракта.
3. Подготовить PHP-прокси на новый фиксированный путь и подключить Android после интеграционных проверок. Приёмка использует изолированную тестовую среду и синтетические данные.

| Сценарий приёмки | Ожидаемый результат |
| --- | --- |
| Действующая capability и подтверждённая пара | Карточка соответствует назначению в том же снимке, что и статус. |
| Чужой заказ, неверный HMAC или просроченный доступ | Карточка закрыта, запрос не даёт выбрать чужой заказ. |
| Переназначение, отзыв, серверная блокировка, завершение или отмена | Старые сведения не выдаются следующим чтением. Запоздавший ответ не заменяет новый на клиенте. |
| Старый заказ без G2-связки, неполный профиль | Статус сохраняется, неизвестные данные скрыты. |
| Два одновременных события обновления одной сессии | Один HTTP-запрос статуса, без второго чтения карточки. |
| Старый клиент | Сохраняются прежний ответ v1 и текущее поведение бронирования. |
