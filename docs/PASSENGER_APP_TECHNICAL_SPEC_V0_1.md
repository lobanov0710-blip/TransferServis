## 2. Назначение и рамки

**Назначение:** пассажир оформляет междугородний трансфер, видит достоверный статус своего заказа, после назначения получает сведения о машине и водителе, отслеживает автомобиль, общается с водителем текстом, по обычному телефону и через интернет, получает подтверждения и историю.

**Главный принцип:** критически важная функция бронирования уже работает и не должна ухудшиться ради нового интерфейса. Новые возможности подключаются к действующему `orderId`, а не создают дублирующие сущности заказа.

**Основной сервис:** пассажирский трансфер, прежде всего Нижний Новгород ↔ Москва. Другие направления не запрещать искусственно на уровне интерфейса, если они разрешены сервером.

**Границы текущего Android:** один локальный профиль и одна текущая защищённая сессия заказа. Многопользовательские аккаунты, несколько одновременно управляемых текущих заказов и новая identity-модель — отдельный проект (`ОТЛОЖЕНО`).

**Тарифы мобильного приложения:** `comfort` / «Комфорт», `business` / «Бизнес», `minivan` / «Минивэн». «Комфорт+» не добавлять.

## 3. Архитектура, которую нельзя ломать

| Репозиторий | Ответственность |
|---|---|
| [TransferServis](https://github.com/lobanov0710-blip/TransferServis) | Java + XML, Fragment, MVVM/LiveData, Retrofit/OkHttp, Room, защищённая сессия AndroidKeyStore/AES-GCM, пассажирский интерфейс. `minSdk=24` не повышать без отдельного решения. |
| [TransferDriver](https://github.com/lobanov0710-blip/TransferDriver) | Принятие и выполнение назначенных заказов, GPS-публикация, чат, входящие/исходящие звонки, FCM водителя. |
| [uber-v3](https://github.com/lobanov0710-blip/uber-v3) | Авторитетные заказы и назначения в Cloudflare D1, проверка staff/passenger access, серверная бизнес-логика, уведомления, новые защищённые API. |
| [public_html](https://github.com/lobanov0710-blip/public_html) | Сайт и существующий HTTPS PHP-шлюз пассажира; серверная передача в Worker по HMAC. |

**Существующий маршрут заказа:** Android → `/api/calculate.php` → расчёт/quote → `/api/order.php` → D1; `/api/order-status.php` → серверное подтверждение статуса своего заказа. Пассажирский клиент не вызывает приватный staff Worker API напрямую. Действующий `API_CONTRACT_V1.md` имеет статус FROZEN: новые контракты добавлять отдельно/с версионированием без скрытого изменения v1.

**Статусы заказа (не менять):** `new`, `taken`, `in_progress`, `done`, `canceled`. Состояния «назначен», «прибыл», «в пути до точки подачи» не выводить произвольно из GPS или из `in_progress` — при необходимости проектировать отдельные подтверждаемые события.

## 5. Уже согласованные новые функции

### 5.1. Назначенный автомобиль и карта Mapbox — `СОГЛАСОВАНО`

| ID | Требование | Критерий приёмки |
|---|---|---|
| MAP-01 | Экран «Моя поездка» расширяет существующий `ActiveOrderFragment`, не заменяя восстановление заказа. | При `new` отсутствуют водитель/машина и кнопки связи; при `taken/in_progress` они доступны только при подтверждённом назначении. |
| MAP-02 | Показать имя водителя, марку/модель/цвет/госномер только из проверенной серверной карточки назначенного автомобиля. | Неизвестное поле скрыто/отмечено недоступным, не генерируется из шаблона. |
| MAP-03 | Использовать Mapbox Maps SDK для карты, позиции назначенного автомобиля и её плавного перемещения. | Маркер принадлежит только текущему назначению; при смене назначения старые координаты скрываются. |
| MAP-04 | GPS поступает из TransferDriver, Worker проверяет активный заказ, owner-driver и качество точки; пассажир получает ограниченную read-only проекцию. | По чужому `orderId/driverId` получить GPS нельзя; нельзя публиковать точку за другого водителя. |
| MAP-05 | Статус свежести GPS и корректное отображение отсутствия сети/позиции; остановка отслеживания при `done/canceled`. | Устаревшая позиция не называется «сейчас»; терминальный заказ не возвращает текущую точку. |
| MAP-06 | Лицензия Mapbox для автомобильного отслеживания и совместимость с `minSdk=24` проверяются до SDK/production интеграции. | Есть письменное/договорное разрешение на требуемый use-case либо выбран допустимый альтернативный провайдер; `minSdk` без согласия не меняется. |

**Технические границы:** ориентир GPS 5–10 секунд **не является SLA**; лимиты, срок актуальности и частота выбираются после нагрузочных/батарейных тестов. D1 — источник истины назначения; последнее местоположение живёт в отдельном краткоживущем хранилище без истории трека по умолчанию. Для фонового GPS водителя нужна Android Foreground Service и корректное разрешение пользователя. Пассажирскому приложению GPS-разрешение не требуется для просмотра автомобиля.

### 5.2. Чат пассажир ↔ назначенный водитель — `СОГЛАСОВАНО`

| ID | Требование | Критерий приёмки |
|---|---|---|
| CHAT-01 | Переписка один-на-один в рамках одного действующего назначения и `orderId`. | Соседний/чужой заказ и прошлый водитель не могут читать/отправлять сообщения. |
| CHAT-02 | Текст, время отправки, история сообщений, обработка повторного нажатия/сети. | Повторная отправка с тем же clientMessageId не создаёт дубликатов. |
| CHAT-03 | Сообщения — в авторитетном серверном хранилище; FCM — только оповещение. | При пропущенном push переписка восстанавливается запросом к серверу. |
| CHAT-04 | При смене водителя и терминальном статусе новые сообщения запрещаются. | Сервер отклоняет попытки неавторизованных/бывших участников. |

Срок хранения переписки, возможность просмотра истории после поездки, лимиты вложений и доставки — `ОТКРЫТО`. **В первой версии вложения и голосовые сообщения не обещать.**

### 5.3. Два обязательных вида звонка — `СОГЛАСОВАНО`

| ID | Требование | Критерий приёмки |
|---|---|---|
| CALL-01 | «Позвонить» предлагает **«По телефону»** и **«Через интернет»**. | Оба варианта доступны при действующем назначении, отсутствующий канал честно помечается как недоступный. |
| CALL-02 | Обычный звонок открывает системную звонилку через `ACTION_DIAL` с разрешённым сервером номером актуального водителя. | Вызов не совершается автоматически; `CALL_PHONE` для этого сценария не требуется; номер не раскрывается неучастникам. |
| CALL-03 | Интернет-звонок — аудио TransferServis ↔ TransferDriver через WebRTC или технически равнозначный проверенный VoIP-стек. | Разговор проходит по сети без обязательной SIM; есть принять/отклонить, завершить, занято/ошибка, тайм-аут. |
| CALL-04 | Отдельный защищённый signaling, STUN/TURN, Android microphone permission, входящие вызовы через системно допустимый UX, FCM-уведомления. | Вызов проверяет права обоих участников при создании/принятии; фон/заблокированный экран тестируются отдельно. |
| CALL-05 | Интернет-звонок не переключается на тарифицируемый телефонный без явного выбора. | При обрыве VoIP есть предложение позвонить по телефону, но автоматического телефонного вызова нет. |
| CALL-06 | Запись звука по умолчанию отсутствует. | Аудиозапись не создаётся и не сохраняется ни клиентом, ни сервером. |

**Открытые вопросы:** VoIP-провайдер либо собственная инфраструктура, TURN/реле и стоимость, ограничения регионов, требования к входящим звонкам, политика телефонных номеров и юридические согласия.

### 5.4. Общие правила назначенной поездки

- `new`: «Ожидаем назначения водителя»; никаких выдуманных данных водителя.
- `taken`: отображать подтверждённое назначение; карта/чат/звонки только когда сервер удостоверил участников.
- `in_progress`: действующее назначение сохраняет доступ, но описания стадии поездки должны соответствовать данным backend.
- `done/canceled`: остановить GPS-подписку и публикацию, новые сообщения и вызовы запретить; историю заказа сохранить.
- **Reassignment:** моментально отозвать доступ прежнего водителя; не отображать его текущую геопозицию, номер и чат как актуальные.
- **Security:** существующий `passenger_order:read` token не считать универсальным разрешением отправлять чат или инициировать звонок; для write-действий определить отдельную scoped capability или документированную проверку прав на новом API.

## 7. UX и информационная архитектура

### Текущая навигация — `БАЗА`

`Главная` → расчёт → подтверждение → бронирование → активный заказ; внизу `Главная / Поездки / Профиль`.

### Предложенная эволюция — до согласования

- **Главная:** быстрый расчёт, текущая поездка и значимое серверное состояние; не отображать примеры как реальные бронирования.
- **Моя поездка:** маршрут/дата/тариф/цена/статус, назначенный автомобиль, встроенная Mapbox-карта, отметка свежести GPS, чат и меню звонка.
- **Поездки:** текущая и локальная история; будущая серверная история нескольких заказов не гарантируется существующей моделью одной capability-сессии.
- **Профиль:** имя и телефон (существуют); избранное/настройки — только после решения о новых функциях.
- **Чат:** как экран внутри конкретного заказа; отдельная вкладка «Сообщения» **не утверждена**, не добавлять без UX-решения.
- **Состояния:** loading, empty, error, no-driver, location-unavailable, driver-changed, offline, expired-access, terminal; содержимое доступно при увеличении шрифта и TalkBack.

Стиль продолжает `docs/UI_DESIGN_SYSTEM.md`: Java/XML, Material, тёмный графит, синий функциональный акцент и сдержанный золотой брендовый. Без миграции на Compose/Kotlin.

## 8. Модель данных и API: требования к будущим проектам

### Новые данные (предполагаемая модель, НЕ созданная миграция)

- `vehicles` / привязка к staff-водителю: проверенное имя, контактный телефон и отображаемая карточка машины; правила обновления и верификации определяются административным процессом.
- `order_messages`: message ID, order ID, actor, `assignment`/версия назначения (если требуется), текст, timestamp, idempotency key; D1 + индексы/пагинация/retention.
- `trip_call_sessions`: только метаданные вызова/состояния/времени и участники при необходимости; **никакой аудиозаписи**.
- `tracking_current_location`: актуальная точка + точность + время измерения + временная привязка к заказу/назначению, краткий TTL, не авторитетное состояние заказа.

### API-контуры (имена маршрутов пока не утверждены)

1. **Assigned driver presentation:** узкий пассажирский read-only ответ с проверенной карточкой водителя и машины; не раскрывать staff-поля, JWT или приватные идентификаторы.
2. **GPS publish:** staff auth + D1-проверка назначения и статуса, нормализация/лимиты GPS.
3. **GPS read:** passenger capability + PHP HMAC, проверка конкретного заказа/назначения/TTL.
4. **Chat read/send:** separate write authorization, текущая привязка, rate limiting, дедупликация, pagination.
5. **Call signaling/start/accept/end:** отдельные scoped credentials/TTL, проверка обоих участников, ограниченный срок жизни сессии, обработка гонок.
6. **FCM passenger registration:** отдельная регистрация/отзыв токена устройства, проверка владения и жизненного цикла; FCM не подменяет D1.

Все новые endpoints и поля должны пройти контрактное ревью и быть реализованы в соответствующем репозитории. Действующие `/calculate`, `/orders`, `/order-status`, `/api/*.php` не переписывать без отдельного решения. Никаких секретных backend/HMAC ключей или приватных staff-JWT внутри Android APK.

## 9. Безопасность и конфиденциальность

- Минимально необходимый доступ по конкретному заказу/назначению; сервер проверяет каждого отправителя и читателя при каждом запросе.
- Действующие capability и staff-credentials защищены и не размещаются в URL, сообщениях, push, логах и аналитике.
- TLS на внешней и внутренней границе, no-store для ответов с GPS и личными данными, защита от перебора, spam/rate-limits, replay и дублирующей отправки.
- При смене водителя отзываются текущие доступы к звонкам/чату/GPS предыдущего назначения.
- GPS хранить минимально (только последняя точка и freshness), не использовать для скрытого круглосуточного мониторинга.
- Запрашивать разрешения Android в контексте понятной функции, без принудительного GPS пассажира ради карты.
- Политика персональных данных, срок хранения сообщений и метаданных, согласия водителя/пассажира и региональные правовые ограничения — `ОТКРЫТО` до релиза.
- VoIP: защищённое аудио, без записи; TURN и signaling рассматриваются как чувствительная инфраструктура. Телефонный звонок — только по выбору пользователя.
- Ошибка отправки FCM или обрыв сети не должны делать базу заказа «неподтверждённой» и не должны вести к повторному созданию заказа.

## 10. Нефункциональные требования

| ID | Требование | Как проверяем |
|---|---|---|
| NFR-01 | Совместимость с `minSdk=24` или согласованное исключение | CI, выбор корректной версии SDK, запуск Android-эмуляторов; повышение minSdk — только отдельным решением. |
| NFR-02 | Жизненный цикл Android | Поворот/сворачивание/возврат/убийство процесса/перезапуск не создают новый заказ и не подменяют назначенного водителя. |
| NFR-03 | Достоверность | Время GPS и статусы берутся из серверных данных; UI маркирует недоступные и устаревшие сведения. |
| NFR-04 | Доступность | TalkBack, масштабирование шрифта, контрастность, состояния без сети, понятные сообщения ошибок. |
| NFR-05 | Энергоэффективность | GPS водительского приложения работает только в разрешённом сценарии и с адаптивной частотой; замеры батареи и трафика до релиза. |
| NFR-06 | Масштабируемость/стоимость | Нагрузочные тесты GPS/polling/chat/VoIP; лимиты и бюджеты Mapbox, TURN, Cloudflare/FCM проверяются до production. |
| NFR-07 | Наблюдаемость | Метрики доставки/ошибок без GPS-траекторий, содержимого чата, телефонов и токенов в логах. |
| NFR-08 | Управляемость выпуска | Feature flags и обратимая миграция/rollout; новые функции не мешают существующему заказу, когда выключены. |

**Не выдумывать численные SLA:** p95 API, задержку GPS, delivery rate, число одновременных вызовов, месячный бюджет и retention записать измеримыми значениями после выбора инфраструктуры и проверки в CI/E2E.

## 11. Сценарии приёмки (минимальные end-to-end)

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| E2E-01 | Расчёт → создание заказа → закрытие/перезапуск | Тот же заказ и корректный серверный статус, без нового POST заказа. |
| E2E-02 | Водитель принимает заказ | Пассажир получает назначение и проверенную карточку, чужому пассажиру доступ запрещён. |
| E2E-03 | Водитель передаёт GPS, пассажир открывает карту | Видна только свежая позиция назначенного водителя и отметка времени. |
| E2E-04 | GPS устаревает, водитель меняется или заканчивает заказ | Старая точка не показывается как актуальная, лишние доступы аннулированы. |
| E2E-05 | Чат в обе стороны, дубли и переподключение | Сообщения не дублируются; посторонний не имеет доступа; потеря push не теряет историю. |
| E2E-06 | По телефону | Открывается системный dialer с разрешённым номером; никакого автоматического вызова. |
| E2E-07 | Через интернет | Вызов через сеть, входящий экран, согласие обеих сторон, разговор, завершение, обработка обрыва и фона. |
| E2E-08 | Отменён/завершён, попытка GPS/chat/call | Сервер отказывает в новых действиях; история заказа остаётся корректной. |
| E2E-09 | Недействительный passenger capability / staff JWT | Закрытый отказ без утечки данных чужой поездки, без удаления действующей сессии из-за сетевого сбоя. |
| E2E-10 | Отключены новые feature flags | Старый заказ, тариф, профиль, история, расчёт и оформление продолжают работать. |

**Контроль качества:** unit, API-contract, security/authorization, Android instrumentation на изолированных AVD и ограниченные E2E. Для backend `npm test` + `wrangler deploy --dry-run` до merge. Проводить отдельные тесты без создания случайных production-заказов/реальных звонков и push, если этого специально не разрешено. Отчёт должен отличать локальный тест, CI, staging и реальный production E2E.

## 13. Открытые продуктовые решения для следующего обсуждения

1. **Состав ближайшего выпуска:** только базовые функции + согласованные MAP/CHAT/CALL либо включить отдельные PROP-01—04?
2. **Возможность менять/отменять заказ:** правила сроков, финансовые последствия, кто подтверждает изменение, что делать после назначения водителя?
3. **Профиль и повторные поездки:** оставляем одну локальную сессию заказа или планируем отдельную серверную авторизацию для нескольких устройств?
4. **Карты и связь:** доказать правомерность use-case в лицензии Mapbox; выбрать WebRTC signaling/TURN, бюджет/доступность; не считать провайдеры выбранными автоматически.
5. **Персональные данные:** кто может вводить/подтверждать карточку водителя и машины, кто видит номер, срок хранения истории чата, правила обращения с GPS и возможность подменного телефона.

После ответа владельца на эти вопросы выпускать **v0.2** с зафиксированными приоритетами и отдельными техническими интерфейсами; после его явного утверждения — формировать исполнимый backlog и этапные PR.

## 14. Правила изменения этого ТЗ

- Версия и дата меняются при изменении scope; решения владельца сопровождаются ссылкой/точной формулировкой.
- Новые предложения сначала получают статус `ПРЕДЛОЖЕНО`, а не автоматически `СОГЛАСОВАНО`.
- Изменение FROZEN API v1, Android minSdk, полномочий пассажира, server-side price и order lifecycle требует отдельного review.
- Каждая реализация имеет критерии приёмки, тесты, подтверждение владельца и подтверждённый факт deploy; документация/CI не равны публикации.
