# PUSH-02H — явный выход из активной поездки

Дата: 04.11.2026. Статус: Draft поверх Android PUSH-02G PR №37. Нет production deployment.

## Назначение

На экране активной поездки добавлена отдельная кнопка **«Убрать поездку с устройства»**. Это действие удаляет локальную read-capability для просмотра заказа, **не отменяет поездку, не меняет статус заказа в D1 и не равнозначно отзыву push на сервере**.

### Два несмешиваемых сценария

1. **Подтверждённый сервером отзыв** (в будущем, когда отдельно разрешён `PASSENGER_PUSH_NETWORK_ENABLED=true`): явный выбор пассажира → загрузить текущую encrypted session и проверить order ID экрана → revoke-only grant → подтверждённый DELETE регистрации → `clearIfMatches` для той же сессии и подтверждённо отозванного installation ID. Если сервер ответил 403/429/503, недоступен, либо прислал `ok=false`, локальная сессия **сохраняется**. UI показывает «отзыв на сервере не подтверждён», даёт повторную попытку или **отдельный** двухшаговый локальный выход. Автоматических повторов нет.
2. **Только на устройстве** (доступно и при выключенном FCM): пользователь видит отдельное предупреждение об отсутствии подтверждения серверного отзыва и о том, что заказ НЕ отменяется, затем явно подтверждает. Лишь после этого на worker thread происходит `PassengerOrderSessionStore.clearIfMatches` по exact session snapshot и order ID экрана. Никакого FCM/HTTP вызова и удаления installation ID; возможную устаревшую регистрацию на сервере обязаны ограничивать TTL и future maintenance.

При одновременном создании новой сессии `clearIfMatches` отклоняет очистку: чужой заказ не удаляется. На ошибке сети/ошибке хранилища нельзя показывать ложное сообщение об успехе. Если сервер подтвердил DELETE, но локальная запись завершилась с ошибкой, отдельные статусы показывают это прямо. Логировать токены/read grants/FCM payload запрещено.

## Технические изменения

- `ui/active/PassengerSessionExitAction.java`: независимый от Fragment worker-side диспетчер с отдельными состояниями `LOCAL_ONLY_CLEARED`, `REMOTE_NOT_CONFIRMED`, `REMOTE_CONFIRMED_*`, `SESSION_CHANGED` и `LOCAL_STORAGE_FAILED`. В Production/Debug `BuildConfig.PASSENGER_PUSH_NETWORK_ENABLED=false`: **remote ветка не выполняет HTTP**.
- `ui/active/ActiveOrderFragment.java`: два разных подтверждения в MaterialAlertDialog; выход виден в SUCCESS и ERROR статусах, чтобы при временной ошибке загрузки поездки пользователь не оказался заблокированным. Действия выполняются через однопоточный executor, UI не блокируется. После подтверждённого удаления перечитывается актуальная сессия. Повторное нажатие в процессе запрещено.
- `ActiveOrderViewModel.getSessionOrderIdForExit()` выдаёт только **не секретный orderId**; access token не передаётся в аргументы Fragment, диалоги, Parcelable или логи.
- `PassengerOrderSessionStore.clearIfMatches` теперь использует **`commit()` вместо `apply()`**. Это позволяет не возвращать успешный выход до сохранения факта удаления токена на диске и при неудаче вернуть ошибку. Остальные защищённые свойства сессии не менялись.
- Разметка и русские строки обеспечивают явное предупреждение «не отмена заказа / нет серверного подтверждения».
- Нет новой D1 migration, API, Firebase sender, включения флага, реальных заказов или удалённого сервера.

## Тесты

- JVM `PassengerSessionExitActionTest`: remote-disabled не вызывает сеть и не очищает данные; локальный выход только при явном режиме; mismatch/смена сессии не удаляет новый заказ; remote exception не превращается в подтверждение; результаты server-confirmed vs local-only не путаются.
- Изолированный API35 `PassengerExplicitExitUiTest`: с фиктивным read-JWT в Android Keystore принудительно отображает ошибку получения статуса (не обращаясь к production), проверяет реальное предупреждение, отмену без очистки и явное удаление только локальной сессии.
- `.github/workflows/push-02a-registration-gate.yml` включает новую проверку в API35 и наблюдает пути активной поездки, нового Test и документа.
- Стандартные Debug/Release unit, lint, compile instrumentation, MockWebServer и unsigned release проверки GitHub Actions обязательны на финальном SHA.

## Известные ограничения

- **Это выход из локального доступа к поездке, не полноценная система аккаунтов и не отмена заказа.**
- `PASSENGER_PUSH_NETWORK_ENABLED=false`, реальный серверный logout пока недоступен и не утверждён. UI не должен пытаться отправить запрос при этом флаге.
- После «только на устройстве» уже существующая backend регистрация не отзывается, а installation ID сохраняется (для дальнейшей безопасной очистки). До FCM rollout требуется согласовать retry/retention/read-token expiry UX.
- Автоматическая очистка повреждённой/истёкшей сессии и переход к другой поездке не используют полноценный push revoke. Перед включением FCM требуется аудит **всех** таких путей, а также завершение зависимых серверных/ PHP PR.
- Действующий код Android не может отменить рейс этим действием; серверные операции отмены бронирования — отдельный будущий этап.

Основная среда — production, STAGING только для необходимых тестов. Никаких merges, запуска production Worker, D1 writes, PHP/FCM сетевых действий, подписания APK или деплоя без разрешения владельца.
