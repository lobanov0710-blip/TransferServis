# Android Transfer Servis — тестовое окружение (Debug)

**Статус (27.10.2026):** PHP Gateway и Android Debug прошли ручные E2E-проверки в отдельном staging. Проверены авторизация, HMAC, расчёт, создание и идемпотентная повторная отправка заказа, чтение статуса, восстановление сессии после перезапуска и потеря/восстановление интернет-соединения на эмуляторе. Изменения Android остаются в черновике PR; проверки безопасности staging и Android instrumentation ещё не завершены.

## Архитектура

Пассажирское Android-приложение по-прежнему написано на **Java + XML** с архитектурой MVVM. Для запросов сохраняются Retrofit и OkHttp.

```text
Android Debug
  → отдельный HTTPS PHP-шлюз staging
  → uber-v3-staging (подпись HMAC проверяется здесь)
  → transfer-servis52-staging (D1)
```

PHP-шлюз подписывает запросы к Worker. HMAC-секрет Worker хранится **только на PHP-сервере**, не в APK. API-маршруты не меняются: `api/calculate.php`, `api/order.php`, `api/order-status.php`.

Android Release, как и раньше, обращается к `https://transfer-servis52.ru/`. Только Debug может использовать тестовый адрес.

Debug имеет отдельный `applicationId` (`ru.transferservis.app.staging`), поэтому устанавливается отдельно от Release (`ru.transferservis.app`) и не использует его хранилище данных. Не переносить тестовые токены или данные в Release.

## Локальная конфигурация разработчика

**Только после** отдельного согласования и публикации защищённого staging PHP-хоста поместить в непубликуемый файл `%USERPROFILE%\.gradle\gradle.properties` на Windows:

```properties
transferStagingBaseUrl=https://staging.transfer-servis52.ru/
transferStagingAccessToken=TEMPORARY_STAGING_ONLY_TOKEN
```

Адрес staging уже подтверждён. `TEMPORARY_STAGING_ONLY_TOKEN` — только заполнитель: действительный токен берут из локального файла `ts52-staging-secrets/staging-access.key`, не публикуют и не отправляют в чат. Путь URL должен оканчиваться `/`, а имя хоста должно содержать `staging`.

Тестовый токен является временным: он попадёт в собранный Debug APK. Debug APK **нельзя публиковать или передавать посторонним**. После E2E-испытаний тестовый токен перевыпускаем. Никогда не помещаем секрет Worker или персональные данные клиентов в `gradle.properties`.

Если `transferStagingBaseUrl` не задан, Debug использует заведомо неработающий `https://staging-not-configured.invalid/`. Это исключает случайную отправку тестового заказа в production при запуске Debug без настроек. Release не содержит тестового токена.

## Что проверяется без реального сервера

- Код Android не переводился с Java на Kotlin.
- Retrofit-контракт, модель заказа, защищённое хранилище Keystore/AES-GCM и механизм восстановления заявки не переписаны.
- HTTP-тест с MockWebServer проверяет заголовок `X-Staging-Access-Token` и отсутствие HMAC-заголовков Worker.
- CI выполняет unit-тесты, Lint, сборку debug APK и компиляцию Android instrumentation APK. Сам эмулятор CI не запускает.

## Безопасный запуск инструментальных тестов Android (QA AVD)

Обычный GitHub Actions проверяет JVM-тесты, Lint, сборку и компиляцию androidTest APK, но **не выполняет** инструментальные тесты на устройстве. Существующие androidTest очищают `passenger_profile`, `passenger_order_session` и другие тестовые данные. **Не запускать** `:app:connectedDebugAndroidTest` на общем наборе ADB-устройств: это затронет эмулятор с тестовой заявкой.

Для Windows предусмотрен сценарий `scripts/run-staging-instrumentation.ps1`. Он:

1. Собирает оба Debug APK с заведомо несуществующим `https://staging-not-configured.invalid/` и **пустым** `transferStagingAccessToken`, не обращаясь к staging или production API.
2. Создаёт новый временный Android AVD с установленным x86_64 system image API 36+, выделяет ему `emulator-5556` и проверяет, что этот номер не занят.
3. Устанавливает оба APK **только** на новый временный эмулятор, выполняет все `am instrument -w` тесты; сохраняет лог в `%TEMP%\TransferServis_Instrumentation\`.
4. Завершает и удаляет только созданный им AVD; пересобирает обычный Debug APK согласно локальным Gradle-настройкам. Установленный ранее `emulator-5554` не перезапускает, данные заказа не очищает.

Нужны Android SDK Command-line Tools (latest) и установленный x86_64 Android 36+ system image. Скрипт не обновляет remote/GitHub/Timeweb, не передаёт токены в сеть и **не запускается автоматически при получении PR**.

Из корня репозитория на правильной ветке:

~~~powershell
git pull --ff-only origin feature/android-staging-debug-gateway-v1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-staging-instrumentation.ps1
~~~

Итогом должен стать `QA_INSTRUMENTATION_PASSED=True` и сохранённый локальный отчёт. Если возникнет ошибка, приложить только диагностическую строку и имя отчёта, не копировать токены. **Подтверждено 27.10.2026:** Android 36.1 x86_64, `emulator-5556`, все 27 инструментальных тестов успешны. Первый запуск не смог создать userdata из-за нехватки свободного пространства (образ Android 37 запрашивал 12 ГБ); второй был отклонён из-за размера раздела 2048 МБ (максимум эмулятора 2047 МБ). В третьем запуске скрипт с образом Android 36.1 и параметром `-partition-size 2047` завершил тесты успешно. Повторный прогон без новых изменений не нужен.

## После отдельного разрешения на развёртывание

1. Администратор развёртывает отдельный PHP staging-хост согласно PR №5 репозитория `public_html`; production-шлюз не меняется.
2. Проверить HTTPS, ACL, лимиты запросов, отдельные серверные HMAC-файлы и временный токен.
3. Выполнить на Android Debug расчёт → создание заказа → локальное сохранение сессии → принудительный перезапуск → `/order-status`.
4. Проверить восстановление при потере сетевого ответа, отсутствие дубликатов в staging D1 и отсутствие Telegram/FCM уведомлений.
5. После тестов отозвать тестовый токен. Слияния в основные ветки — только после приёмки.

**Работающий production-сайт, сервер, БД, заявки клиентов и Telegram/FCM в этом PR не изменяются.**
